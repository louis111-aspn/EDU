Controlling — Profitability Analysis. 수익성 분석의 두 가지 방식과 역사적 맥락
💡
CO-PA는 제품·고객·채널·지역 등 다차원 관점에서 기여이익(Contribution Margin)을 분석하는 SAP Controlling의 핵심 모듈입니다. 영업·마케팅·원가 부서가 함께 활용하는 내부 관리 보고의 엔진입니다.
두 방식의 역사적 등장

SAP ECC(R/3) 시절부터 CO-PA에는 두 가지 방식이 공존했습니다. Costing-Based CO-PA는 사용자 정의 Value Field에 원가·수익을 기록하는 방식으로 유연성과 즉시성이 강점이었습니다. Account-Based CO-PA는 G/L 계정 구조를 그대로 활용하여 FI와의 정합성이 높았지만, 분석 유연성과 성능 면에서 뒤처졌습니다.

국내에서 Costing-Based가 압도적으로 사용된 이유
단순한 관성이 아닙니다. 5가지 구조적 원인이 있었습니다.
📌
ECC 시절 글로벌 시장에서도 Costing-Based가 주류였으나, 국내는 제조업 중심 산업 구조와 관리회계 문화가 맞물려 그 경향이 더욱 강했습니다.
5가지 구조적 원인
  • 1
    원가 중심 관리회계 문화
    한국 대기업·제조업은 제품별 원가 구성요소 분해(재료비/노무비/제조간접비/판매관리비)를 경영 보고의 핵심으로 요구합니다. Costing-Based의 Value Field 자유 설계는 이 요구를 그대로 수용했지만, Account-Based는 G/L 계정 구조에 종속되어 유연성이 부족했습니다.
  • 2
    표준원가 차이 분석(Variance Analysis) 요건
    국내 제조업은 차이 범주별(Price Variance / Quantity Variance / Lot-Size Variance 등) 세분 분석을 경영층 보고에 활용합니다. ECC 시절 Account-Based는 총 차이(Total Variance)만 제공해 사실상 사용 불가 수준이었습니다.
  • 3
    간접비 배부 유연성 요건
    한국 기업은 CO-CCA(코스트센터 회계)에서 CO-PA로의 정교한 배부 로직(Assessment Cycle, Activity-Based)을 CO-PA에 반영하는 요건이 강합니다. Costing-Based의 PA Transfer Structure는 이를 세밀하게 제어할 수 있었습니다.
  • 4
    FI 조정 부담의 상대적 수용
    국내 SAP 구축 시장은 월마감 시 CO-PA와 FI 간 조정(Reconciliation)을 별도 운영 프로세스(Excel + 체크리스트)로 이미 정착시켜 왔습니다. "조정이 쉽다"는 Account-Based의 장점이 상대적으로 선택 유인이 되지 못했습니다.
  • 5
    컨설턴트·레퍼런스 관성 (Lock-in)
    ECC 시절 국내 주요 SI 파트너의 Best Practice 템플릿이 Costing-Based 기반으로 구축되어 있었고, 이것이 S/4 전환 시에도 "기존 방식 유지" 압력으로 작용했습니다.
⚠️
위 5가지 이유 중 ①②③은 S/4HANA에서 Margin Analysis가 기술적으로 해결했습니다. ④⑤는 기술 문제가 아닌 거버넌스·변화관리 문제로 S/4 전환 프로젝트에서 여전히 저항 요소로 작동합니다.
SAP가 Costing-Based를 포기한 이유
개발 중단 선언의 배경 — 3가지 전략적 결정
🚨
SAP 공식 입장: Costing-Based CO-PA는 S/4HANA On-Premise에서 기술 지원은 유지하나 신규 기능 개발 없음(Frozen). S/4HANA Cloud(Public)에서는 사용 불가. 모든 신규 투자(Fiori, SAC, Joule AI)는 Margin Analysis에만 집중.
이유 1. Universal Journal 아키텍처와의 근본적 충돌

S/4HANA는 FI와 CO 전반의 데이터를 ACDOCA 단일 테이블에 저장하는 구조로 전환했습니다. HANA In-Memory 기술로 인해 Account-Based 대비 Costing-Based가 가졌던 성능 우위가 더 이상 유효하지 않습니다. Costing-Based의 별도 CE 테이블 구조는 이 통합 아키텍처와 본질적으로 상충합니다.

❌
Costing-Based: CE1~CE4 별도 테이블 → ACDOCA와 이중 저장 → 아키텍처 낭비
✅
Margin Analysis: ACDOCA 단일 저장 → 모든 모듈이 같은 데이터 공유
이유 2. "단일 진실 공급원(Single Source of Truth)" 원칙

S/4HANA의 핵심 설계 철학은 외부회계(FI)와 내부회계(관리회계)를 하나의 데이터 구조로 통합하는 것입니다. FI와 CO-PA가 서로 다른 테이블에 분리된 채 월마다 조정 작업이 필요한 구조는 이 철학과 정면으로 충돌합니다. SAP는 "FI와 CO를 위한 분리 데이터 구조는 고객에게 복잡성을 강요한 구조적 실수였다"고 사실상 인정했습니다.

이유 3. Cloud 전략 및 Clean Core 원칙

SAP의 전략적 방향인 RISE with SAP, Clean Core와 Costing-Based는 양립하기 어렵습니다. S/4HANA Cloud Public에서는 Margin Analysis만 사용 가능(Mandatory)하며, Costing-Based는 아예 활성화할 수 없습니다.

배포 형태Costing-BasedMargin Analysis
S/4HANA On-Premise사용 가능 (단, 개발 중단)권장
S/4HANA Cloud Private제한적 지원권장
S/4HANA Cloud Public (RISE)사용 불가필수 (Mandatory)
📌
SAP가 Costing-Based를 "포기"한 것은 기능이 나빠서가 아닙니다. HANA + Universal Journal이라는 새로운 아키텍처가 과거의 한계를 제거하면서, 더 단순하고 정합성 높은 Margin Analysis가 동일한 요건을 충족할 수 있게 되었기 때문입니다.

Margin Analysis의 해결
FI와 Margin Analysis가 동일한 ACDOCA를 읽으므로 수치는 항상 자동 일치. 별도 조정 작업 불필요. FI 영업이익 = Margin Analysis CM I (설계상 항상 동일)
✅
월마감 시간이 단축되는 가장 직접적인 이유입니다.
🎙️ 강사 노트 "여기서 FI 영업이익(+4,500원)과 CO-PA 기여이익(+3,500원)의 차이가 보이시죠? FI에서 할인을 매출차감으로 처리하면 최종 숫자는 일치시킬 수 있을지 모릅니다. 하지만 Costing-Based CO-PA의 진짜 조정 문제는 단순히 특정 계정 하나의 처리 방식 때문이 아닙니다. 매출과 할인의 전기 시점 차이, 표준원가와 실제 차이가 반영되는 구조적 불일치, 그리고 G/L 계정과 Value Field 간의 기호 체계 차이 등 복합적인 요소가 얽혀서 발생합니다. 바로 이 구조적 한계 때문에 과거 현장에서는 매월 엑셀 체크리스트를 돌리며 야근을 할 수밖에 없었던 것이고, S/4HANA의 Margin Analysis는 이 근본적인 구조를 ACDOCA 하나로 통합하여 해결한 것입니다."
Step 5. 수주 견적 단계 — Costing-Based만의 고유 강점
📌
이 영역은 Margin Analysis가 아직 구조적으로 대체하지 못하는 부분입니다. SAP의 대안은 SAC Planning입니다.

⚠️ 여전히 남아 있는 과제 (국내 관점)
  • 1
    Actual Costing 연계의 복잡성
    Margin Analysis에서 실제원가(CKMLCP) 기반 COGS 재평가는 가능하나, Variance Splitting과 COGS Actual Price 재평가를 동시 활성화 시 이중 전기 발생 제약이 존재합니다. 실제원가 사용 기업은 반드시 사전 설계에 반영해야 합니다.
  • 2
    Value Field 유연성의 부재
    Account-Based는 G/L 계정 구조에 종속됩니다. 비재무 분석 축(영업사원별, 채널별 기여이익)을 표현하려면 계정 체계 자체를 확장해야 합니다. Costing-Based에서는 Value Field 추가만으로 해결되던 요건입니다.
  • 3
    계획(Planning) 기능의 전환 복잡성
    기존 Costing-Based 기반 계획 프로세스를 SAC Planning으로 재설계하는 것은 상당한 프로젝트 투자를 요구합니다. SAC 도입 없이는 수주 단계 기여이익 예측 기능이 공백이 됩니다.
  • 4
    레거시 Report Painter 리포트 재구축
    ECC 시절 Costing-Based 기반으로 구축된 수백 개의 Report Painter 리포트는 Fiori 또는 SAC 기반으로 전면 재구축이 필요합니다. 기술 이슈가 아닌 거버넌스·변화관리 리스크입니다.

S/4HANA 전환 프로젝트에서 CO-PA 방식 선택의 기준
🎯
SAP 공식 입장 요약: On-Premise에서 Costing-Based 기술 지원 유지하나 신규 개발 없음(Frozen). Cloud는 Margin Analysis만 가능. 모든 신규 기능(Fiori, SAC, Joule AI)은 Margin Analysis에만 투자.
프로젝트 유형별 권고
프로젝트 유형권고 방향핵심 근거
신규 구축 (Greenfield) Margin Analysis만 Costing-Based 선택 = 3~5년 내 재전환 부담 자초. 처음부터 COGS Split + Variance Splitting 설계 필수.
전환 (Brownfield) Combined → 단계 이관 Combined CO-PA 전략으로 전환기 Costing-Based 병행 운영 후 Margin Analysis로 순차 이관.
Cloud(RISE) 전환 Margin Analysis만 Public Cloud는 Costing-Based 선택지 자체가 없음. 사전에 SAC Planning 포함한 전체 아키텍처 설계 필요.
핵심 설계 원칙 4가지
  • 1
    COGS Split Profile을 초기 설계에 포함
    나중에 추가하면 기존 전표의 데이터 정합성 문제 발생. 반드시 Day 1 설계에 포함해야 합니다.
  • 2
    Variance Splitting 구성을 사전 결정
    "어떤 차이를 어떤 G/L 계정으로 분리할 것인가"를 원가 담당자와 함께 초기에 설계. 후속 변경 시 비용 큼.
  • 3
    SAC Planning 포함 여부를 아키텍처 단계에서 결정
    수주 단계 기여이익 예측이 비즈니스 요건에 있다면, SAC 없이는 Margin Analysis만으로 충족 불가. 범위에 포함 여부를 초기에 결정해야 합니다.
  • 4
    보고 아키텍처를 Fiori + SAC 조합으로 재설계
    ECC 시절 Report Painter 리포트는 재구축이 필요합니다. 이를 기술 부채가 아닌 보고 혁신의 기회로 프레이밍하는 변화관리가 핵심입니다.

최종 결론

Costing-Based CO-PA는 ECC 시대의 훌륭한 솔루션이었습니다. 하지만 S/4HANA에서 COGS Split, Variance Splitting, ACDOCA 통합이라는 3가지 혁신이 도입되면서, Margin Analysis는 Costing-Based가 제공하던 분석 깊이에 도달했고 여기에 "FI와의 구조적 자동 일치"라는 결정적 우위를 추가했습니다.

국내 S/4HANA 전환 프로젝트에서 Costing-Based를 유지하려는 관성은 이해할 수 있습니다. 그러나 그것은 기술적 판단이 아닌 변화 회피입니다. 올바른 설계와 변화관리를 전제로 한다면, Margin Analysis는 이미 국내 요건을 충분히 충족하는 성숙한 솔루션입니다.
