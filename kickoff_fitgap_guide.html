SECTION 01
Kick-off 준비
계약 직후 72시간 — 이 시간이 프로젝트 전체 분위기를 결정한다
Kick-off의 두 가지 목적

Kick-off 미팅은 인사 자리가 아닙니다. 두 가지 명확한 목적이 있습니다.

목적 1 — 범위 재확인
제안서에서 합의된 범위를 프로젝트 팀 전원이 동일하게 이해하고 있는지 검증합니다. 특히 고객 담당자가 영업 단계에서 배제되었던 경우, 범위에 대한 기대치 차이가 크게 나타납니다.
목적 2 — 거버넌스 수립
의사결정 권한자, 커뮤니케이션 채널, 이슈 에스컬레이션 경로를 확정합니다. 이것이 Kick-off에서 합의되지 않으면 프로젝트 중반에 결정권자가 없는 상태로 표류하게 됩니다.
⚠ 흔한 실수

Kick-off를 "프로젝트 소개 PT"로 준비하는 경우입니다. 고객은 이미 우리가 무엇을 할지 알고 있습니다. Kick-off에서 중요한 것은 앞으로 어떻게 함께 일할 것인가의 합의입니다.

방법론별 Kick-off 준비 포인트
GR 구현 — SAP Activate

• 프로젝트 헌장(Project Charter) 초안 지참 — 범위, 마일스톤, 역할/책임 포함

• Phase 게이트(Gate) 기준 사전 제시 — 각 단계 종료 조건 명시

• 고객 측 시스템 오너 확정 요청 — GR 설정 변경 권한자

• SAP 라이선스 및 릴리즈 버전 확인 — S/4HANA 버전에 따라 GR 기능 차이 존재

SAC-P — Agile/Sprint 0

• Product Backlog 초안 지참 — 우선순위 미확정이어도 무방

• Sprint 주기, 리뷰/회고 일정 합의 — 고객 담당자 참석 가능 여부 확인 필수

• Product Owner 역할 담당자 확정 요청 — 백로그 우선순위 결정권자

• SAC 테넌트 접근권 및 기존 모델 현황 파악

항목내용미합의 시 리스크

이슈 에스컬레이션 N일 내 미결 이슈 → 상위 책임자 보고 기준 HIGH 이슈 방치 → 리스크 확대
산출물 검토 기한 컨설턴트 제출 후 고객 피드백까지 N영업일 MID 일정 계획 무력화

착수 단계 실수 사례 — 드릴

상황: Kick-off 미팅 2주 후 고객 담당자가 갑작스럽게 교체되었습니다. 신임 담당자는 제안서 내용을 모르는 상태였고, 범위 전반에 대한 재설명 요청이 들어왔습니다.

예방: Kick-off 직후 범위 요약 문서(1~2페이지)를 고객에게 서면으로 전달합니다. 담당자 교체가 발생해도 이 문서가 인수인계 근거가 됩니다. 또한 Kick-off 의사록에 참석자 서명 또는 이메일 확인을 반드시 받아야 합니다.

상황: 착수 후 SAP 환경을 확인했더니 고객사가 S/4HANA 2020 버전을 사용 중이었습니다. 제안서에서 가정했던 Group Reporting 일부 기능이 해당 릴리즈에서 제한적으로 지원됨을 뒤늦게 발견했습니다.

예방: 제안 단계에서 SAP 릴리즈 버전을 가정 조건으로 명시하고, Kick-off 전에 반드시 실제 버전을 확인합니다. S/4HANA 버전별 GR 기능 지원 범위(예: ICMR, Top-side Adjustment 등)를 사전 매핑해 두는 것이 좋습니다.

상황: 고객이 지정한 Product Owner가 실무 담당자였으나 실제 설계 방향 결정은 CFO 라인의 승인이 필요했습니다. 스프린트 리뷰마다 "상위 보고 후 확정"이 반복되며 스프린트 주기가 사실상 2배로 늘어났습니다.

예방: Kick-off에서 "Product Owner는 스프린트 리뷰 당일 백로그 우선순위와 기능 컨펌을 최종 결정할 권한이 있어야 한다"는 조건을 명문화합니다. 결정권이 상위에 있다면 스프린트 주기를 처음부터 더 길게 설정하거나 의사결정 구조 자체를 재설계해야 합니다.

SECTION 02
AS-IS 인터뷰 설계
무엇을 묻고, 무엇을 듣고, 무엇을 기록할 것인가
AS-IS 인터뷰의 목적 — 현황 파악이 아니다

AS-IS 인터뷰를 "현재 업무 방식 파악"으로만 이해하면 얕은 수준에 머무릅니다. 진짜 목적은 세 가지입니다.

목적 1
Pain Point 발굴
→
목적 2
숨겨진 요구사항 포착
→
목적 3
Fit-Gap 판정 근거 수집

특히 숨겨진 요구사항을 포착하는 것이 핵심입니다. 고객은 자신이 원하는 것을 항상 명확하게 말하지 않습니다. "현재 이렇게 하고 있습니다"라는 설명 뒤에 "그래서 사실 이게 불편합니다"가 있고, 그 뒤에 "정말로는 이렇게 되었으면 합니다"가 숨어 있습니다.

인터뷰 기록 원칙 — 들은 것과 해석한 것을 분리하라

인터뷰 메모에서 가장 흔한 실수는 고객이 말한 것과 컨설턴트가 해석한 것을 구분하지 않는 것입니다. 나중에 "그런 말 한 적 없다"는 분쟁이 생깁니다.

✗ 나쁜 기록 방식

"고객은 내부거래 대사를 자동화하고 싶어한다. → ICMR 구현 필요."

→ 고객 발언과 컨설턴트 해석이 뒤섞여 있습니다.

✓ 좋은 기록 방식

[고객 발언] "매월 내부거래 대사에 3일이 걸리고 수작업 오류가 많습니다."

[해석] ICMR 자동화 요구 가능성 → Fit-Gap 확인 필요.

POINT

인터뷰 후 24시간 내 메모를 정리하고, 핵심 내용은 고객 담당자에게 이메일로 확인을 요청합니다. "이렇게 이해했습니다 — 맞습니까?"라는 한 문장이 나중의 분쟁을 막습니다.

SECTION 03
TO-BE Visioning
AS-IS를 파악했다면 — 우리는 어디로 가야 하는가
TO-BE Visioning이 왜 Fit-Gap 이전에 필요한가

많은 프로젝트에서 AS-IS 파악 직후 곧바로 Fit-Gap 분석으로 넘어갑니다. 그 결과 Fit-Gap이 "현재 업무를 시스템으로 옮기는 작업"으로 전락합니다. 이것이 구현 후 고객이 "바뀐 게 없다"고 말하는 가장 큰 이유입니다.

TO-BE Visioning은 AS-IS의 Pain Point를 해소한 미래 상태(Future State)를 먼저 그리는 작업입니다. TO-BE가 확정된 이후에야 Fit-Gap은 의미를 가집니다. Fit-Gap = TO-BE와 표준 기능 사이의 거리이기 때문입니다.

AS-IS → TO-BE → Fit-Gap 흐름

AS-IS: 현재 무엇이 문제인가 (인터뷰로 파악)

TO-BE: 문제가 해결된 미래 상태는 어떤 모습인가 (Visioning)

Fit-Gap: TO-BE를 시스템으로 구현하려면 표준 기능으로 어디까지 되고 어디서 막히는가

TO-BE Vision의 두 가지 레벨

TO-BE는 두 레벨에서 동시에 그려야 합니다. 어느 한 레벨만 있으면 Vision이 공허해지거나 지나치게 세부적으로 흐릅니다.

레벨 1 — 비즈니스 Vision

"이 프로젝트가 끝나면 무엇이 어떻게 달라지는가"를 수치와 업무 결과로 표현합니다.

예시 — GR: "월 마감 소요 시간 X일 → Y일 단축" / SAC-P: "계획 수립 사이클 N주 → M주, 시나리오 분석 자동화"

CFO·임원 보고 시 쓰이는 언어입니다. 기술 용어 없이 작성해야 합니다.

레벨 2 — 프로세스/시스템 Vision

비즈니스 Vision을 달성하기 위해 업무 프로세스와 시스템이 어떻게 바뀌는지를 표현합니다.

예시 — GR: "ICMR 자동화 → 수동 Excel 대사 제거, FS Item 재설계 → IFRS 18 세그먼트 보고 자동 생성" / SAC-P: "S/4HANA Live 연동 → 실적 자동 반영, Data Action → Top-Down 배분 자동화"

Fit-Gap 분석의 직접 입력값이 됩니다.

GR 구현 — TO-BE Visioning 핵심 관점

GR 프로젝트의 TO-BE는 연결결산 마감 프로세스의 재설계를 중심으로 그립니다. 단순히 BPC·Excel을 GR로 대체하는 것이 아니라, 마감 프로세스 자체가 어떻게 달라지는지를 명확히 해야 합니다.

시나리오별 수동 계산 (BPC/Excel) Top-side Adjustment 구조화 → 감사 추적 가능 Journal Entry 승인 워크플로우 설계
지분법 평가 수동 처리 IAS 28 기준 GR 내 자동 계산 (범위 내 한도 내) 손실 중단·회복 케이스 수동 병행 구조 확정
⚠ GR TO-BE 설계 시 흔한 실수

BPC의 커스텀 로직을 GR로 1:1 이식하려는 시도입니다. GR의 표준 프로세스를 먼저 이해하고, BPC의 커스텀이 정말 필요한 것인지 TO-BE 단계에서 재검토해야 합니다. 불필요한 커스텀 이식은 유지보수 부담만 늘립니다.

SAC-P 구현 — TO-BE Visioning 핵심 관점

SAC-P 프로젝트의 TO-BE는 계획 수립 사이클의 재설계를 중심으로 그립니다. 데이터 흐름(실적 → 계획 → 분석)과 조직 간 협업 구조가 어떻게 바뀌는지까지 포함해야 합니다.

실적 데이터 수동 복사·붙여넣기 S/4HANA Live 연동 또는 Import 자동화 → 실적 자동 반영 데이터 소스 연결 방식 및 갱신 주기 확정

⚠ SAC-P TO-BE 설계 시 흔한 실수

데이터 모델(차원 구조)을 TO-BE Visioning 단계에서 확정하지 않고 Sprint 중반에 변경하는 경우입니다. SAC-P에서 데이터 모델 변경은 이미 완성된 Data Action·Story를 전면 재작업해야 하는 치명적 리스크입니다. TO-BE Vision 확정과 함께 데이터 모델 초안을 동시에 승인받아야 합니다.

TO-BE Vision 확정을 위한 워크숍 구조

TO-BE Vision은 컨설턴트가 혼자 만들어서 고객에게 제시하는 것이 아닙니다. AS-IS 인터뷰 결과를 바탕으로 고객과 함께 만들어야 고객의 주인의식이 생깁니다.

TO-BE 프로세스 흐름 공동 작성
→
STEP 3
성공 기준(KPI) 수치화 합의
→
OUT
TO-BE Vision 문서 서명
✓ TO-BE Vision 문서 최소 구성

비즈니스 Vision: 달성 목표 수치 (마감 X일 단축, 계획 사이클 Y주 단축 등)

프로세스 Vision: AS-IS → TO-BE 프로세스 흐름 비교도

범위 경계: 이번 프로젝트에서 달성하는 TO-BE vs. 향후 과제

선결 조건: TO-BE 달성을 위해 고객이 선행해야 할 것 (데이터 정비, 조직 변경 등)

상황 (GR): AS-IS 인터뷰에서 "내부거래 대사에 3일 소요"라는 Pain Point를 발견했습니다.

TO-BE Vision 없이 Fit-Gap: "내부거래 대사 기능 구현 → ICMR Fit" 으로 단순 판정. 실제로 Trading Partner 코드 체계가 법인별로 제각각이어서 구현 후에도 자동 대사율이 40%에 불과했습니다.

TO-BE Vision 포함 후 Fit-Gap: "대사율 95% 이상 달성"을 TO-BE 수치로 확정 → Fit-Gap에서 Trading Partner 코드 표준화(Gap-Config), 미매핑 계정 처리 로직(Gap-Enhancement) 이 추가로 식별되어 구현 전 해결.

결론: TO-BE Vision의 수치가 구체적일수록 Fit-Gap의 정확도가 높아집니다.

SECTION 03
Fit-Gap 판정 기준
Fit인가, Gap인가 — 그리고 Gap이라면 어떤 종류인가
Fit-Gap이란 무엇인가

Fit-Gap 분석은 고객의 요구사항(Requirements)과 시스템의 표준 기능(Standard Functionality) 사이의 일치도를 판정하는 작업입니다.

판정의미대응
Fit 표준 기능으로 요구사항을 충족할 수 있음 설정(Configuration)으로 구현
Partial Fit 표준 기능으로 일부 충족 가능, 프로세스 조정 필요 업무 프로세스 변경 + 부분 설정
Gap — Config 표준 기능 내에서 추가 설정으로 해결 가능 추가 설정 공수 반영
Gap — Enhancement 표준 기능을 벗어난 커스터마이징 필요 (ABAP 등) 개발 공수 및 유지보수 비용 별도 산정
Gap — 3rd Party 외부 솔루션 연동으로만 해결 가능 인터페이스 개발 + 외부 벤더 협의
⚠ 중요

Gap을 발견했을 때 즉각적인 개발(Enhancement) 결론을 내리는 것은 금물입니다. 먼저 업무 프로세스 변경으로 해결할 수 없는지를 검토해야 합니다. 개발은 항상 유지보수 부담을 수반합니다.

GR 구현 — 대표적 Fit-Gap 판정 포인트
요구사항 예시판정 경향주의 사항
법인 간 내부거래 자동 대사 Fit ICMR 표준 기능 Trading Partner 설정 선행 필요
지분법 평가 (IAS 28) Partial Fit GR 표준 지원, 단 손실 중단·회복은 수동 조정 병행
특정 그룹사 커스텀 제거 분개 Gap — Enhancement ABAP 개발 또는 Top-side Journal 활용 여부 판단
IFRS 18 신규 계정 분류 보고 Gap — Config FS Item 재설계 필요, 릴리즈 버전 지원 여부 확인
다통화 환산 (IAS 21) Fit 환산 방법(전기말/평균) 설정 확인
세그먼트 보고 (IFRS 8) Partial Fit Profit Center 구조와 연결 범위 매핑 필요
SAC-P 구현 — 대표적 Fit-Gap 판정 포인트
요구사항 예시판정 경향주의 사항
매출 계획 Top-Down 입력 Fit 표준 입력 모델 데이터 모델 설계(차원 구조) 사전 확정 필요
비용 Bottom-Up 계획 취합 Partial Fit Data Action으로 집계 로직 구현, 복잡도에 따라 공수 증가
BOM 전개 기반 제조원가 계획 Gap — Config SAC 표준 미지원 → 별도 Data Action 또는 외부 연산 필요
실적 데이터 자동 연동 (S/4HANA) Fit Live Connection 네트워크 레이턴시 및 데이터 볼륨 사전 점검 필요
계획 시나리오 버전 관리 Fit 표준 버전 기능 버전 명명 규칙 및 잠금 정책 합의 필요
외부 ERP(비SAP) 실적 연동 Gap — 3rd Party Import 방식 또는 중간 ETL 레이어 검토 필요
Fit-Gap 판정 시 가장 어려운 순간 — Gap인지 요구사항 과잉인지

때로는 Gap처럼 보이는 것이 실제로는 요구사항 과잉인 경우가 있습니다. 표준 기능으로 충분한데 고객이 익숙한 방식을 고집하는 경우입니다.

판단 기준

"이 요구사항이 충족되지 않으면 업무(결산/보고/계획 수립)가 불가능한가?"

"아니라면, 표준 기능으로 업무 목적을 달성할 수 있는 대안이 있는가?"

이 두 질문에 답할 수 있어야 Gap 여부를 확정할 수 있습니다.

고객 요구: 기존 Excel 계획 시트와 동일한 레이아웃으로 SAC에서 입력하고 싶다.

잘못된 대응: 즉시 커스텀 개발 검토 → 공수 폭증.

올바른 대응: SAC 표준 입력 화면(Input Form)이 제공하는 기능을 먼저 시연합니다. 고객이 원하는 것은 "Excel 레이아웃"이 아니라 "빠르고 편한 입력"인 경우가 대부분입니다. 표준 Input Form 커스터마이징 범위(열 순서, 집계 표시 등)로 해결 가능한지 먼저 검증해야 합니다.

SECTION 04
Gap 문서화
발견한 Gap을 어떻게 기록하고, 고객과 합의하는가
Fit-Gap 문서의 구성 요소

Fit-Gap 문서는 단순한 목록이 아닙니다. 각 항목이 왜 Gap인지, 어떤 대안이 있는지, 고객이 선택해야 할 것은 무엇인지가 담겨야 합니다.

항목기재 내용필수/선택
요구사항 ID추적 가능한 고유 번호 (예: GR-FG-001)필수
요구사항 설명고객 인터뷰에서 포착한 요구사항 원문 또는 요약필수
판정Fit / Partial Fit / Gap-Config / Gap-Enhancement / Gap-3rd필수
표준 기능 설명표준으로 어디까지 지원되는지 명시필수
Gap 설명Gap이 발생하는 이유 — 업무 요건과 표준 기능의 차이Gap 시 필수
대안 솔루션프로세스 변경 / Config / 개발 / 3rd Party 등 옵션 제시Gap 시 필수
추가 공수 예상대안 구현에 필요한 공수(Man-Day) 개략 산정권장

Gap 문서화의 핵심 원칙
✗ 피해야 할 패턴

"Gap 발견 → 개발 필요 → 공수 추가" 식의 단선적 문서화.

고객은 선택지를 받지 못하고, 개발 비용만 통보받는 구조가 됩니다.

✓ 권장 패턴

"Gap 발견 → 대안 A, B, C 제시 → 각 대안의 공수/리스크 비교 → 고객 결정 요청".

고객을 의사결정 주체로 세우면 나중의 클레임을 막습니다.

Gap 합의 워크숍 — 어떻게 진행하는가

Fit-Gap 문서를 작성하면 반드시 고객과 함께 검토하는 워크숍을 진행해야 합니다. 이메일로 문서를 보내고 "확인 요청"하는 방식은 대부분 피드백 없이 끝납니다.

STEP 1
Fit 항목 일괄 확인
→
STEP 2
Partial Fit 프로세스 조정 협의
→
STEP 3
Gap 대안 선택 결정
→
STEP 4
의사록 서명/이메일 확인
⚠ STEP 3이 가장 중요하다

Gap 대안 선택은 반드시 고객이 결정해야 합니다. 컨설턴트가 "이 방향이 좋겠습니다"라고 결론 내리면, 나중에 문제가 생겼을 때 "그때 컨설턴트가 그렇게 하라고 했다"는 책임 전가가 발생합니다. 대안을 제시하되 결정은 고객에게, 결정 근거는 반드시 문서화해야 합니다.

방법론별 Gap 처리 우선순위 기준
GR — Waterfall/Gate

Blueprint/Realization Phase 경계 전에 모든 Gap의 대안이 확정되어야 합니다. Realization 중 Gap이 추가 발견되면 일정에 직접 영향을 줍니다.

우선순위 기준: 월 마감 Critical Path에 영향을 주는 Gap → High. Enhancement(개발) Gap은 가능한 초반에 확정해야 개발 일정을 확보할 수 있습니다.

SAC-P — Agile/Sprint

Gap은 백로그 항목으로 관리됩니다. Sprint 0(Discovery)에서 High 우선순위 Gap을 식별하고 초기 스프린트에 배치합니다.

우선순위 기준: 계획 수립 핵심 흐름(매출→비용→손익)을 막는 Gap → Sprint 1~2 배치. 보고 형식 Gap은 후반 스프린트로 조정 가능합니다.

Q1. TO-BE Visioning이 Fit-Gap 분석보다 먼저 이루어져야 하는 이유는?
① 고객에게 프로젝트 일정을 먼저 보여주기 위해
② Fit-Gap은 TO-BE와 표준 기능 사이의 거리를 측정하는 것이므로, TO-BE가 없으면 Fit-Gap 판정 기준 자체가 없기 때문이다
③ AS-IS 인터뷰 결과를 검토할 시간이 필요하기 때문이다
④ 고객의 예산을 미리 파악하기 위해
Q1. Kick-off 미팅에서 반드시 합의해야 하는 가장 중요한 항목은?
① 프로젝트 팀 소개 및 역할 인사
② 전체 제안 내용 PT 재발표
③ 의사결정 권한자, 커뮤니케이션 채널, 이슈 에스컬레이션 기준 등 거버넌스 수립
④ 프로젝트 완료 후 유지보수 계획 협의
Q2. AS-IS 인터뷰 메모 작성 시 가장 중요한 원칙은?
① 최대한 상세하게 모든 발언을 받아 적는다
② 고객이 말한 것(발언)과 컨설턴트가 해석한 것을 명확히 분리해 기록한다
③ 결론만 간단히 요약해 기록한다
④ 인터뷰 종료 후 일주일 내에 정리하면 충분하다
Q3. Fit-Gap 분석에서 Gap이 발견되었을 때 가장 먼저 해야 할 것은?
① 즉시 개발(Enhancement) 공수를 산정해 고객에게 통보한다
② 업무 프로세스 변경으로 표준 기능 내에서 해결할 수 없는지 먼저 검토한다
③ Gap을 프로젝트 범위에서 제외하고 다음 단계로 넘어간다
④ 경쟁사 솔루션을 먼저 확인한다
Q4. SAC-P 프로젝트에서 "매출 계획 Top-Down 입력" 요구사항의 일반적인 Fit-Gap 판정은?
① Fit — SAC 표준 입력 모델로 구현 가능
② Gap-Enhancement — 커스텀 개발 필요
③ Gap-3rd Party — 외부 솔루션 필요
④ Partial Fit — 업무 프로세스 전면 변경 필요
Q5. Gap 합의 워크숍에서 Gap 대안의 최종 선택은 누가 해야 하는가?
① 기술적 판단이 어려운 고객을 대신해 컨설턴트가 결정한다
② 프로젝트 PM이 비용 효율을 고려해 결정한다
③ 대안과 각 대안의 공수/리스크를 제시하고, 최종 선택은 반드시 고객이 결정하도록 한다
④ 가장 저렴한 대안을 자동으로 선택한다
