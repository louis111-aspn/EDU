00

오프닝 — 왜 이 교육이 필요한가

고객이 요청한 것을 정확히 구현했는데, 왜 Go-Live 3개월 후 전면 재설계를 요청했을까?

실제 사례 | ERP 구매 모듈 구현 프로젝트

고객 요청: "구매 발주서를 입력하면 자동으로 재고에 반영해 주세요."
→ 주니어 개발자는 요청 그대로 구현 완료.
6개월 후: 부분 납품 처리 불가 / 반품 시 재고 음수 발생 / 공급업체별 단가 이력 추적 불가
→ 전면 재설계 요청

주니어 vs. 시니어 사고 패턴
✗ 주니어의 사고 패턴
고객이 말한 것을 그대로 구현하는 것이 목표
요구사항 = 완전한 명세
현재 케이스만 검토 ("이렇게 하면 되지 않나?")
화면/기능 단위로 분리해서 생각
"일단 동작하면 성공"
✓ 시니어의 사고 패턴
고객이 말한 것 뒤에 있는 의도를 파악
요구사항 = 출발점, 질문이 필요
예외 케이스 / 미래 변경 가능성까지 설계
데이터의 생명주기 전체를 추적
"이것이 바뀌면 무엇이 깨지는가?"
핵심 명제: 고객의 말(Requirement)과 고객의 진짜 필요(Need)는 다르다.
What을 구현하라는 지시보다 Why가 필요한가를 먼저 파악하는 습관이 핵심 역량이다.
01

데이터 모델링 함정

화면을 보고 테이블을 만들면 안 되는 5가지 이유

함정 1-1
화면 = 테이블 착각
주문서 화면 칸 그대로 컬럼 설계 → 부분취소·분할배송 추가 요청 시 전면 재설계
함정 1-2
주소·이력 분리 미흡
고객 테이블에 주소 직접 저장 → 주소 변경 시 과거 배송 이력도 바뀜 (데이터 오염)
함정 1-3
Status 컬럼 남용
status = 'Y'/'N' 단순화 → 중간 상태(보류·검토 중)·이력 추적 전면 불가
함정 1-4
코드성 데이터 하드코딩
부서코드를 IF문에 직접 박아 넣기 → 조직 개편 때마다 개발자 수작업 수정
함정 1-5
시간 축 미반영
Effective Date 없이 현재 값만 저장 → 급여·조직 소급 계산 시 기준 데이터 없음
실전 케이스
Case 1-1 · ERP 구매/재고 — 주문 화면을 그대로 DB로 옮기면? ▾

✗ 잘못된 설계 (화면 기반)

컬럼타입문제점
order_idINT PK
customer_nameVARCHAR고객 변경 시 이력 없음
item_nameVARCHAR품목 여러 개면?
qtyINT부분납품 불가
statusVARCHAR중간 상태 표현 불가
addressVARCHAR배송지 변경 이력 없음

✓ 올바른 설계 (생명주기 기반)

orders (주문 헤더) order_id | customer_id (FK) order_date | status_cd order_lines (품목별 라인) line_id | order_id (FK) item_id (FK) | qty_ordered qty_shipped order_status_log (상태 이력) log_id | order_id (FK) status_cd | changed_at changed_by customers / addresses (분리) customer_id | name address_id | valid_from | valid_to
사고 전환: 테이블을 설계하기 전에 먼저 묻기 — "이 주문이 부분 취소되면? 배송지가 바뀌면? 품목이 추가되면?" 화면(View)과 저장 구조(Model)는 다르다.
Case 1-3 · 1-5 · ERP 회계/HR — Status 단순화와 시간 축 누락 ▾

✗ status = 'Y' / 'N'

· 가능한 상태: 2가지
· 결재 중 / 보류 / 반려 표현 불가
· 상태 변경 시각 기록 없음
· 누가 바꿨는지 추적 불가
· 감사(Audit) 요건 충족 불가

✓ 상태 코드 + 이력 테이블 분리

· 상태 코드 테이블 별도 관리
· status_log: 변경 시각 + 변경자 기록
· 새 상태 추가 시 코드 변경 없음
· 감사 추적(Audit Trail) 자동 확보
· 평균 처리 시간 등 통계 산출 가능

✗ 현재 값만 저장 (Effective Date 없음)

employees emp_id | name | salary -- 급여 인상 시 이전 값 소실 -- 소급 계산 불가

✓ Effective Date 패턴 적용

salary_history emp_id | amount effective_from | effective_to -- 특정 시점 조회: -- WHERE eff_from <= :date -- AND eff_to >= :date
공통 원칙: '현재 상태'만 저장하면 과거와 미래를 잃는다. 비즈니스 데이터는 거의 모두 '언제부터 언제까지'라는 시간 축이 필요하다.
핵심 질문: 이 데이터는 '언제', '어떻게' 바뀔 수 있는가를 먼저 물어야 한다
02

프로세스 로직 구현 함정

업무 담당자가 설명한 정상 흐름은 전체 로직의 20%에 불과하다

함정 2-1
Happy Path만 구현
정상 결제만 구현 → 부분환불·타임아웃·이중결제 케이스 누락 [CRM 영업관리]
함정 2-2
순서 의존성 미고려
전표 마감 전 수정 허용 → 회계 불일치 / 승인 전 다음 단계 진입 허용 → 내부통제 구멍 [ERP 회계]
함정 2-3
예외를 버튼으로 해결
특수 케이스마다 '예외처리' 버튼 추가 → 6개월 후 버튼 30개짜리 화면 탄생
함정 2-4
동시성 미고려
재고 차감 로직에 Lock 없음 → 동시 주문 시 마이너스 재고 발생 [ERP 재고·MES]
함정 2-5
UI에서만 유효성 검증
화면 우회(직접 API 호출) 시 승인 없이 처리 → 내부통제 완전 무력화 [ERP·HR]
실전 케이스
Case 2-1 · CRM 영업관리 — Happy Path만 구현한 결과 ▾

주문 접수 → 결제 요청 → 재고 차감 → 배송 처리 → 완료 (주니어가 구현한 정상 흐름만)

누락 케이스실제 발생 문제도메인
결제 타임아웃결제 요청 후 응답 없음 → 재시도 시 이중결제CRM
재고 부족 (부분)10개 주문인데 7개만 있음 → 부분 승인/대기 처리 로직 없음ERP·재고
결제 취소 후 재고결제 취소 시 차감된 재고 자동 복구 로직 없음ERP·재고
배송 중 주소 변경배송 중 고객이 주소 변경 요청 → 변경 시점 기준 처리 없음CRM
중복 주문 방지새로고침·네트워크 지연으로 동일 주문 2회 생성전 도메인
사고 전환: 로직 구현 전, 'WHEN 이 단계가 실패하면 / 지연되면 / 건너뛰면?' 질문을 각 단계마다 반복하라
Case 2-4 · MES — 재고 동시 차감과 Lock 미처리 ▾

✗ Lock 없는 코드

def deduct_stock(item_id, qty): stock = db.get_stock(item_id) # 100 if stock >= qty: db.update_stock(item_id, stock - qty) # A: 100 조회 → B: 100 조회 # A: 20으로 업데이트 # B: 20으로 업데이트 ← 음수!

✓ 해결 방법

-- 비관적 Lock SELECT * FROM stock WHERE item_id = :id FOR UPDATE; -- 다른 트랜잭션 대기 -- 낙관적 Lock (version 컬럼) UPDATE stock SET qty = qty - :n, version = version + 1 WHERE id = :id AND version = :expected_ver;
Case 2-5 · ERP — UI 전용 승인 로직의 위험성 ▾
✗ UI에서만 검증
화면: 결재 완료 전 '발주 확정' 버튼 비활성화 (JS)
Postman으로 API 직접 호출 → 검증 우회
결재 없이 발주 5건 감사에서 발견
내부통제 완전 무력화
✓ 서버에서 재검증
API 진입 시 결재 상태 DB에서 재확인
미결재 상태면 400 에러 반환
UI는 UX 보조 수단일 뿐
비즈니스 규칙 = 서버 + DB 레이어
핵심 질문: '이 로직이 실패하면 어떤 일이 벌어지는가?'를 먼저 역방향으로 생각해야 한다
03

요구사항 해석 함정

고객이 말한 것은 솔루션이지 요구사항이 아니다

함정 3-1
솔루션을 요구사항으로 착각
"엑셀 업로드 기능 만들어 주세요" → 실제 필요: 배치 자동화 [ERP·HR]
함정 3-2
현행 프로세스 그대로 전산화
오프라인 결재 문서 구조를 DB에 그대로 복제 → 종이 결재의 비효율도 함께 복제됨
함정 3-3
빈도 낮은 예외에 과잉 투자
연 1회 케이스에 복잡한 화면 개발 → 개발 비용 > 예외 처리 비용
함정 3-4
묵시적 비즈니스 룰 누락
"마감은 매월 말일" → 공휴일이면? 주말이면? 윤달이면? 아무도 먼저 말하지 않는다
Case 3-1 · 5 Whys 적용 — HR 근태 엑셀 업로드 요청
요청
고객의 말
"근태 데이터를 엑셀로 업로드하는 기능을 만들어 주세요"
Why 1
첫 번째 이유
매월 초 전 직원 근태 데이터를 HR 시스템에 넣어야 해서
Why 2
두 번째 이유
출입통제 시스템에서 export한 파일을 수작업으로 입력 중
Why 3
근본 원인
출입통제 시스템과 HR 시스템이 별도로 운영되어 연동 없음
해결
진짜 해결책
엑셀 업로드 X → 출입통제 시스템 API 연동 또는 야간 배치 자동화
Case 3-4 · 묵시적 비즈니스 룰 체크리스트
고객이 말한 것아무도 말하지 않은 규칙
"마감은 매월 말일"공휴일·주말이면 전 영업일로 이동
"연체 이자는 다음달 1일부터"1일이 휴일이면 다음 영업일 기산
"급여는 25일 지급"25일 휴일이면 24일(전), 금요일이면 목요일
"재고 마감은 분기 말"해외 법인은 현지 시간 기준 적용
체크리스트: 요구사항 수신 후 → ① Why가 필요한가 ② 현재 어떻게 하고 있나 ③ 예외 케이스가 있나 ④ 관련 시스템이 있나 ⑤ 이 기능이 없으면 무슨 일이 생기나
04

워크어라운드와 기술 부채

워크어라운드는 선택이 아니라 '판단'이다

패턴 4-1
플래그 컬럼 남용
IS_SPECIAL_CASE_2, FLAG_B, FLAG_X → 6개월 후 의미 불명 컬럼 누적 → 담당자 퇴사 시 블랙박스화
패턴 4-2
배치로 정합성 보정
실시간 처리 불가 → 야간 배치로 보정 → 낮 동안 데이터 신뢰 불가 → 배치 실패 시 오류 누적
패턴 4-3
하드코딩된 예외 처리
IF customer_id = 'CUS001' THEN... → 예외 업체 증가 시 코드 폭증 → 테스트·배포 없이 수정 불가
패턴 4-4
문서 없는 워크어라운드
이유 모르게 돌아가는 로직 → 담당자 퇴사 후 아무도 손 못 댐 → "건드리면 터진다" 문화
워크어라운드 허용 vs. 재설계 판단 매트릭스
판단 기준✓ 워크어라운드 허용⚠ 재설계 필요
발생 빈도연 1~2회 이하월 1회 이상
영향 범위단일 사용자/부서다수 사용자·시스템 전체
데이터 신뢰도보조 데이터에 국한핵심 트랜잭션 데이터
확장 가능성이 케이스로 종결유사 케이스 증가 예상
감사 요건내부통제 미해당회계·법무 감사 대상
워크어라운드 도입 시 최소 원칙: ① 왜 이 방법을 선택했는가 (배경) ② 어떤 조건에서 실행되는가 ③ 언제 제거/개선할 것인가 (기한 명시)
Case 4-1 · MES — 플래그 컬럼 누적 실사례
-- 6개월 차 work_order 테이블 (실제 사례) work_order_id INT status VARCHAR -- '대기'/'진행'/'완료' IS_URGENT CHAR(1) -- Y/N (납기 임박) IS_REWORK CHAR(1) -- Y/N (재작업 지시) IS_HOLD CHAR(1) -- Y/N (보류) IS_SPECIAL_LINE CHAR(1) -- Y/N (특수 라인 전용) FLAG_A CHAR(1) -- ??? (개발자 퇴사, 의미 불명) FLAG_B CHAR(1) -- ??? (레거시, 삭제 불가) IS_EXPORTED CHAR(1) -- Y/N (외부 시스템 전송 여부)

✗ 문제

· 플래그 의미를 아는 사람 없음
· 삭제했다가 시스템 오류 발생
· 신규 개발자 온보딩 불가
· 결국 시스템 교체 결정

✓ 올바른 설계

work_order_attributes wo_id | attr_key attr_value | created_at work_order_status_log wo_id | status changed_at | changed_by
05

시니어처럼 생각하는 법

길은 하나가 아니다 — 구현 전 3가지 경우의 수를 먼저 그려라

사고 도구 1 — 3-Option Rule

"월말 마감 후 잔여 재고를 익월로 이월하는 로직을 구현해 주세요" (ERP 재고)

Option A — 배치 프로그램
장점
구현 단순 / 기존 패턴 재활용
단점
실행 실패 시 익월 데이터 없음
재실행 로직 별도 필요
적합 상황
소규모·이월 데이터 단순 구조
Option B — 마감 트랜잭션 즉시 이월
장점
원자성 보장 / 실패 시 롤백
별도 배치 불필요
단점
마감 처리 시간 증가
마감 로직 복잡도 상승
적합 상황
데이터 정합성 최우선
Option C — 기간 파라미터 조회
장점
이월 작업 자체 불필요
과거 임의 시점 조회 가능

Closing

주니어에서 시니어로 가는 길은
'더 많은 코딩'이 아니라 '더 깊은 질문'에서 시작된다

01
고객의 말(Requirement)과 진짜 필요(Need)는 다르다
고객이 '엑셀 업로드'를 요청할 때 진짜 의도는 '대량 데이터를 빠르게 넣고 싶다'는 것이다. 'What을 구현하라'는 지시보다 'Why가 필요한가'를 먼저 파악하는 습관이 핵심 역량이다.
02
데이터는 현재가 아닌 시간 축 위에 존재한다
비즈니스 데이터는 생성·변경·삭제·보관의 생명주기를 가진다. '지금 이 값이 맞는가'보다 '이 값이 언제부터 언제까지 유효한가'를 먼저 설계해야 한다.
03
길은 하나가 아니다 — 설계는 선택이고 선택에는 근거가 필요하다
처음 떠오른 방법이 최선인 경우는 드물다. 최소 3가지 방법을 나열하고, '왜 이 방법을 선택했는가'를 동료와 미래의 자신에게 문서로 설명할 수 있어야 한다.
