Section 01 — Objective

무엇을 조정하려는 것인가

연결 당기순이익 총액과 NCI 자본잔액은 그대로 유지하면서, 손익계산서의 귀속 표시(Presentation)만 조정하는 것이 목적이다
우선주 NCI 귀속분 조정금액 50
조정 전 — Current State
연결 당기순이익 1,000
└ 지배주주 귀속 850
└ NCI 귀속 150
조정 후 — Target State
연결 당기순이익 1,000 불변
└ 지배주주 귀속 800
└ NCI 귀속 ▲ 200
조정 대상
우선주 NCI 귀속분
  • 우선주를 발행한 자회사의 연결 시, 우선주 배당 상당액을 NCI 귀속으로 추가 표시해야 하는 경우
  • 누적적 우선주의 당기 미선언 배당 — PL 귀속 표시만 조정, BS 자본잔액은 변동 없음
  • 당기 귀속 표시 목적이므로 자본변동표의 NCI 잔액을 건드릴 이유가 없음
동시에 충족해야 하는 두 가지 조건
총손익 불변 + NCI 자본잔액 불변
  • 조건 ① 연결 당기순이익 총액을 변경해서는 안 된다 — 귀속 배분만 바뀌어야 함
  • 조건 ② NCI 자본잔액(BS NCI)을 변경해서는 안 된다 — 표시 조정이 목적임
  • 이 두 조건을 동시에 충족하는 기존 계정이 존재하지 않는 것이 핵심 문제

Section 02 — Account Analysis

기존 계정을 상대계정으로 쓸 수 없는 이유

전제 — GR 수기 전표의 구조적 제약
규칙기반(Rule-Based) 분개는 SAP 엔진이 자동으로 차대를 맞춰준다. 반면 수기 전표(Manual Posting)는 사람이 차변과 대변을 모두 명시해야 한다. NCI 귀속손익에 50을 Cr 전기하려면 반드시 Dr 상대계정이 필요하다.

▶ 카드를 클릭하면 사용 불가 이유를 확인할 수 있습니다

후보 계정 01

PL 당기순이익

GR이 모든 PL 계정 합산 결과를 자동 반영하는 전용 관리 계정. FS Item 마스터에 Leaf로 존재하지만 직접 전기 불가.

직접 전기 불가
후보 계정 02

BS NCI (비지배지분 자본)

NCI 자본잔액 계정. 직접 전기는 가능하나 이번 조정의 목적과 부합하지 않음.

목적 부적합
후보 계정 03

일반 수익·비용 계정

일반 PL 손익 계정. 직접 전기 가능하나 연결 당기순이익 합산 노드에 포함되어 총액이 변동됨.

총액 훼손
후보 계정 카드를 클릭하면 구체적인 사유가 표시됩니다.
Conclusion
세 후보 모두 두 조건 중 하나 이상을 위반한다
PL 당기순이익은 시스템이 차단, BS NCI는 조정 목적 불일치, 일반 손익 계정은 총액 훼손. 쓸 수 있는 기존 계정이 없다.

Section 03 — Solution

전용 조정 계정 생성 및 리포트 표시 설계

귀속 조정만을 위한 전용 Leaf FS Item을 신규 생성하고, 리포트에서 PL 당기순이익과 합산 표시하여 총액에 영향을 주지 않도록 설계한다
신규 생성 계정 설계 조건
NI Adjustment (전용 조정 Leaf)
  • GR 자동 계산의 관리 대상이 아닌 일반 Leaf → 수기 전기 가능
  • 연결 당기순이익 합산 노드(PL Aggregation Node)에 미포함 → 총액 불변
  • BS 계정이 아님 → NCI 자본잔액 불변
  • 리포트 레이아웃에서 PL 당기순이익과 합산 표시되도록 설정 필수
FS Item 마스터 구조 이해
PL 당기순이익이 직접 전기를 막는 이유
  • GR FS Item 마스터에 존재하는 항목은 모두 Leaf — 별도 Node 유형은 없음
  • 단, PL 당기순이익은 SAP가 PL 자동 밸런싱 전용으로 지정한 시스템 관리 계정
  • 사용자 직접 전기 시 자동 계산 결과와 충돌 → 시스템 레벨 차단
  • 합산 노드는 리포트 레이아웃에서 구현 — 마스터 레벨이 아님
수기 전표 구조
전용 조정 계정(NI Adjustment)을 Dr 상대계정으로 사용하여 차대를 맞춘다. BS 계정은 전혀 사용하지 않는다.
수기 전표 — Manual Journal Entry
Dr   NI Adjustment 신규 생성 50
Cr   NCI Attribution (NCI 귀속손익) 직접 전기 가능 50
이 분개가 건드리지 않는 것
영향 없는 계정
  • PL 당기순이익 — 시스템 자동 관리, 이 분개로 변동 없음
  • BS NCI — 사용하지 않음, 자본잔액 불변
  • 수익·비용 계정 — 전혀 건드리지 않음
  • 연결 당기순이익 합산 노드 — NI Adjustment는 미포함
이 분개가 변경하는 것
영향받는 계정
  • NI Adjustment — Dr 50 잔액 발생 (리포트에서 PL 당기순이익과 합산)
  • NCI Attribution (NCI 귀속손익) — Cr 50 → NCI 귀속 표시 증가
  • 리포트 표시상 지배주주 귀속 감소, NCI 귀속 증가
리포트 레이아웃 설정
손익계산서 리포트에서 PL 당기순이익과 NI Adjustment를 동일한 표시 행으로 합산하도록 설정한다. 사용자에게는 하나의 당기순이익으로 표시된다.
리포트 집계 로직 — Report Aggregation
당기순이익 표시 =
   PL 당기순이익 시스템 자동 관리 1,000
   + NI Adjustment 신규 생성 − 50
= 표시상 당기순이익 1,000
합산 표시가 필요한 이유
NI Adjustment 단독 표시 시 문제
  • 조정 계정만 생성하고 합산 설정을 빠뜨리면 당기순이익이 리포트에 두 줄로 분리 표시
  • 사용자는 PL 당기순이익과 NI Adjustment를 별도 항목으로 인식하게 됨
  • 감사인이 당기순이익 계정 구조에 의문을 제기할 수 있음
  • FS Item 설계와 리포트 레이아웃 설계는 반드시 세트로 진행
리포트 설계 원칙
합산 표시 설정 시 확인 사항
  • NI Adjustment가 연결 당기순이익 합산 노드에 미포함되어 있는지 확인
  • NI Adjustment의 잔액이 리포트에서 PL 당기순이익과 net으로 표시되는지 확인
  • 지배주주 귀속 / NCI 귀속의 합계가 표시상 당기순이익과 일치하는지 검증
조정 전
연결 당기순이익1,000
└ 지배주주 귀속850
└ NCI 귀속150
조정 후 (리포트 표시)
연결 당기순이익 1,000 불변
└ 지배주주 귀속800
└ NCI 귀속 ▲200
계정 조정 후 잔액 총액 영향 NCI 자본 영향 리포트 표시
PL 당기순이익 1,000 (자동) 없음 없음 NI Adjustment와 합산 표시
NI Adjustment Dr 50 없음 (합산 노드 미포함) 없음 PL 당기순이익과 합산 → 상쇄
NCI Attribution Cr 50 없음 (NCI 제외 노드) 없음 NCI 귀속 표시 증가
BS NCI 변동 없음 없음 없음 자본변동표 NCI 잔액 불변
Final Result
연결 당기순이익 1,000 유지 · NCI 자본잔액 불변 · 귀속 표시만 조정 완료
두 조건(총손익 불변 + NCI 자본잔액 불변)을 모두 충족하면서 NCI 귀속 표시만 조정하는 구조가 완성된다.

Section 04 — Design Principles

FS Item 설계 시 유의사항

✓
조정 계정 생성과 리포트 설정은 세트
NI Adjustment를 생성하는 순간, 리포트 레이아웃에서 PL 당기순이익과의 합산 표시 설정을 동시에 완료해야 한다. 계정만 만들고 리포트 설정을 빠뜨리면 두 줄 표시 문제가 발생한다.
✓
합산 노드 포함 여부 반드시 확인
NI Adjustment가 연결 당기순이익 합산 노드에 포함되어 있으면 총액이 변동된다. 신규 계정 생성 후 반드시 합산 노드 설정을 검증해야 한다.
✓
이 패턴은 우선주에만 국한되지 않음
총손익과 NCI 자본잔액을 동시에 건드리지 않으면서 귀속 표시만 조정해야 하는 모든 케이스에 동일하게 적용된다. FS Item 설계 단계에서 예외 케이스를 미리 식별하는 것이 중요하다.
!
규칙기반과 수기 전표의 차이 인식
규칙기반 분개에서는 SAP 엔진이 차대를 자동으로 맞춰준다. 수기 전표에서는 이 자동화가 작동하지 않으므로, 같은 목적의 조정도 처리 방법이 다르다는 점을 항상 인식해야 한다.

이 설계 패턴이 시사하는 것
FS Item 설계의 중요성
GR 구축 초기 단계에서 예외 조정 케이스를 미리 식별하고 전용 조정 계정을 설계해 두어야 한다. 구축 후 추가하는 것은 리포트 레이아웃까지 재설계해야 하므로 공수가 크게 증가한다.
고객 컨설팅 포인트
회계법인이 별도 조정 계정을 요구하는 경우, 그 이유가 회계적 판단인지 GR 시스템 제약에 대한 대응인지 구분하는 것이 중요하다. 대부분은 수기 전표의 차대 제약에 대한 실무적 해결책이다.
