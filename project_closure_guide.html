SECTION 01
프로젝트 클로징 프로세스
공식 종료와 실질 종료를 구분하고, 고객 관계를 자산으로 남기는 방법
핵심 개념

공식 종료(Formal Closure)는 계약상 완료 조건 충족과 서명을 의미한다. 실질 종료(Actual Closure)는 고객이 시스템을 스스로 운영할 수 있는 상태가 됐을 때다. 많은 프로젝트가 공식 종료 후에도 컨설턴트에게 의존하는 이유는 실질 종료가 이뤄지지 않았기 때문이다. 두 가지를 모두 완성해야 프로젝트가 끝난다.

1-3. Lessons Learned — 형식 vs. 실질

경고

Lessons Learned 문서의 70%는 "다음에 더 잘하겠다"는 선언으로 끝난다. 실제로 다음 프로젝트에 활용되는 Lessons Learned는 구체적 사건 → 원인 → 재발 방지 조치가 한 세트로 기록된 것이다. "커뮤니케이션을 더 잘하자"는 교훈이 아니다.

형식적 Lessons Learned (무의미)

• 고객 커뮤니케이션을 강화해야 한다

• 일정 관리를 더 철저히 해야 한다

• 요건 정의를 초기에 명확히 해야 한다

• 팀워크가 중요하다

실질적 Lessons Learned (재활용 가능)

• 사건: IC 거래 Trading Partner 미등록 법인이 UAT D-5에 발견. 원인: Fit-Gap 시 신규 자회사 설립 가능성을 연결 범위에 포함하지 않음. 재발 방지: 킥오프 시 연결 범위 변동 시나리오(신설/청산/지분 변동)를 명시적으로 확인하는 체크리스트 추가.

1-4. 종료 회의 — 고객 관계를 자산으로 남기는 방법

종료 회의 어젠다 구성 원칙

종료 회의는 "수고하셨습니다" 자리가 아니다. 고객이 앞으로 독립 운영에 자신감을 갖도록 하는 것이 목적이다. 구성은 다음 순서가 효과적이다.

  • ① 프로젝트 성과 요약 — 수치로. "연결 법인 X개, 자동화율 Y%, Go-Live 일정 달성"
  • ② 미완 항목 인수인계 — Phase 2 항목, 하자보수 대상 결함 목록을 명시적으로 공유
  • ③ 운영 체제 확인 — 고객 내부 Key User, 담당 부서, 에스컬레이션 연락처
  • ④ 하자보수 기간 약속 확인 — 기간, 대응 SLA, 연락 채널
  • ⑤ 향후 협력 가능성 언급 — Phase 2, 운영 유지보수 계약, 추가 기능 구현 등 자연스럽게 연결

하자보수 범위인지 신규 요청인지를 먼저 분류하고, 그에 따라 채널을 분리한다.

① 하자보수 범위라면: 하자보수 SLA 내에서 공식 티켓으로 접수하도록 안내. 비공식 메신저 대응은 기록이 안 남아 나중에 분쟁이 된다.

② 신규 기능 요청이라면: "이 요청은 현재 하자보수 범위를 벗어납니다. 별도 유지보수 계약 또는 다음 Phase 구축 시 다룰 수 있습니다"라고 서면으로 안내.

③ 관계 유지와 범위 방어를 동시에: 거절의 어조가 아닌 "함께 다음을 준비하자"는 프레이밍이 고객 관계를 지킨다. 이 시점의 대화가 Phase 2 계약의 씨앗이 된다.

SECTION 02
하자보수 & 운영 이관
무엇이 하자이고 무엇이 추가 요청인가 — 경계를 지키는 것이 다음 프로젝트를 만든다
핵심 개념

하자보수(Warranty)는 구축 완료 기능이 계약 명세대로 동작하지 않는 결함을 수정하는 의무다. 새로운 기능 추가, 요건 변경, 운영 교육 반복은 하자보수가 아니다. 이 경계가 무너지면 컨설턴트는 무기한 무상 지원을 하게 된다.

2-1. 하자(Defect) vs. 추가 요청(New Request) 판단 기준

2-2. 하자보수 기간 운영 원칙

SLA 명확화

하자보수 기간(통상 3~6개월)과 응답 SLA(Critical 24시간, Major 72시간)를 계약 또는 별도 합의서에 명시한다. 구두 약속은 분쟁의 씨앗이다.

티켓 시스템 운용

모든 하자 요청은 공식 채널(이메일, Jira, ServiceNow 등)로만 접수한다. 메신저 요청은 "공식 채널로 접수해 주시면 즉시 처리하겠습니다"로 안내한다.

경계 침범 시 대응

추가 요청이 하자보수 채널로 들어오면, 즉각 분류하여 "이 요청은 별도 검토가 필요합니다"라고 서면 통보. 무대응이나 비공식 처리는 금물이다.

2-4. Key User 육성 — 컨설턴트의 마지막 역할

Key User가 독립 운영할 수 있는 조건

운영 이관의 최종 목표는 고객 Key User가 컨설턴트 없이 정기 사이클을 실행할 수 있는 상태다. 이를 위해 컨설턴트는 단순 교육이 아닌 "옆에서 한 번, 혼자서 한 번" 방식의 실습 기반 인수인계를 해야 한다.

  • GR: Key User가 직접 월마감 사이클을 실행하고, 컨설턴트는 검토만 하는 회차를 최소 1회 진행
  • SAC-P: Key User가 직접 Data Action을 실행하고 Write-Back 결과를 검증하는 실습 1회 이상
  • 교육 완료 후 "나 혼자 할 수 있다"는 Key User 자기 확인서(간단한 체크리스트) 확보

원칙적으로 추가 요청이다. 다만 상황에 따라 달라질 수 있다.

① Fit-Gap에 해당 거래 유형이 포함되어 있었다면: 구현 누락이므로 하자보수 대상.

② Fit-Gap에 없던 거래 유형이라면: 명백한 신규 요청. 별도 계약 또는 Phase 2로 안내.

③ 판단이 모호하다면: 즉답하지 않고 Fit-Gap 문서를 먼저 확인한 뒤 서면으로 분류 결과를 통보한다. 구두로 먼저 수락하지 않는다.

핵심: 항상 Fit-Gap 문서가 판단 기준이다. 문서가 없으면 모든 요청이 하자로 인정될 수 있다 — Fit-Gap 문서를 잘 남겨야 하는 이유가 여기에 있다.

이 상황은 운영 이관이 완결되지 않았음을 의미한다. 두 가지 방향 중 하나를 선택해야 한다.

① 유지보수 계약 전환: "현재 요청하시는 지원 수준은 별도 유지보수 계약을 통해 공식적으로 제공해드릴 수 있습니다"라고 제안. 이것이 비즈니스적으로도 옳은 방향이다.

② Key User 역량 강화: 고객이 유지보수 계약을 원하지 않는다면, 비공식 지원을 계속하는 대신 Key User가 스스로 해결할 수 있도록 집중 교육 세션 1회를 제안한다.

절대 하면 안 되는 것: 아무런 정리 없이 비공식 지원을 무기한 지속하는 것. 컨설턴트의 시간이 다음 프로젝트에서 사용되어야 할 자원이다.

SECTION 03
컨설턴트 자기 성장
프로젝트 경험을 지식으로 전환하고, 다음 단계를 준비하는 방법
핵심 메시지

프로젝트를 많이 했다고 자동으로 성장하는 것은 아니다. 경험을 구조화하여 언어로 만드는 사람이 성장한다. 시스템을 설정할 줄 아는 사람은 많다. 그 설정이 고객의 비즈니스에 어떤 의미인지를 설명할 수 있는 사람은 드물다.

3-1. 프로젝트 경험을 지식으로 전환하는 방법

프로젝트 종료 직후 — 개인 회고 3단계

프로젝트가 끝나고 2주 이내에 다음 3가지를 개인 노트에 기록한다. 3개월이 지나면 기억이 흐려진다.

  • ① 내가 처음 알게 된 것: 이번 프로젝트에서 처음 접한 기술·업무·고객 패턴. 예: "GR에서 간접지배 법인이 Bottom-up으로 자동 처리되는 구조"
  • ② 내가 실수한 것: 잘못 판단하거나 놓쳤던 것. 솔직하게 기록. 예: "Trading Partner 관리 정책을 킥오프 때 명시하지 않아 UAT에서 문제 발생"
  • ③ 다음에 다르게 할 것: 위의 실수를 반복하지 않기 위한 구체적 행동 변화. 추상적인 결심이 아닌 체크리스트 항목 수준으로 기록.

3-2. 다음 제안을 위한 레퍼런스 구성

주의

레퍼런스 구성 시 고객사명, 담당자명, 특정 수치 등 기밀에 해당하는 정보는 반드시 익명화해야 한다. "국내 대형 제조지주사"처럼 산업·규모를 특정할 수 있는 수준으로 표현한다.

레퍼런스 구성 요소기록 방법활용 시점
프로젝트 개요 산업군, 기업 규모, SAP 제품, 연결 법인 수(GR) 또는 계획 단위 수(SAC-P) 제안서 레퍼런스 섹션
핵심 구현 내용 어떤 Gap을 어떻게 해결했는가. 기술적 난이도와 접근법 고객 프레젠테이션, 역량 증명
정량적 성과 자동화율, 마감 시간 단축, 이관 오류율 등 수치화 가능한 성과 제안서 ROI 섹션, 인터뷰
특이 케이스 일반적이지 않은 구조(다단계 지배구조, 복수 기능통화 등)와 해결 방법 전문성 증명, 내부 교육
고객 피드백 종료 회의에서 받은 피드백, 고객 추천사(가능한 경우) 제안서 신뢰도 강화

3-4. "Beyond Configuration" — 어드바이저로의 전환

시리즈의 핵심 메시지

이 시리즈 전체를 관통하는 메시지는 하나다. T-Code를 입력하는 사람에서 "왜 이렇게 설정해야 하는가"를 설명하는 사람으로 전환해야 한다는 것이다. 고객 CFO에게 "IC 제거 룰을 어떻게 설정했습니다"가 아니라 "이 설정이 귀사의 연결 재무제표 신뢰도에 어떤 의미인지"를 말할 수 있어야 한다.

시스템 구현자의 언어
  • "GR에서 IC Elimination Rule을 설정했습니다."
  • "Data Action에 배분 로직을 구현했습니다."
  • "Transport가 완료되어 PRD에 반영됐습니다."
  • "ACDOCP에 Write-Back이 성공했습니다."
비즈니스 어드바이저의 언어
  • "내부거래 제거 자동화로 연결 마감 오류 리스크가 감소합니다."
  • "이 배분 로직은 사업부별 수익성 분석의 신뢰성을 보장합니다."
  • "변경 이력이 시스템에 기록되어 감사 대응이 가능합니다."
  • "계획 데이터가 실적 시스템과 통합되어 Plan/Actual 분석이 가능해집니다."

3-5. 이 시리즈를 마치며 — 성장의 타임라인

MODULE 1 — 제안 단계
RFP를 읽는 법, 범위 함정을 피하는 법
프로젝트는 계약서에 서명하기 전부터 시작된다. 제안 단계의 판단이 이후 6개월을 결정한다.
MODULE 2 — 착수 · Fit-Gap
첫 인상과 요건의 언어를 정의하는 단계
킥오프의 질이 프로젝트 전체의 톤을 결정한다. Fit-Gap 문서는 이후 모든 판단의 기준이 된다.
MODULE 3 — Implementation
설정하는 것이 아니라 구현하는 것
Transport, CR, 단위 테스트 — 실행 단계의 규율이 품질을 결정한다.
MODULE 4 — UAT · 이관
고객 확인, 그리고 시스템을 넘기는 순간
UAT는 버그 발견이 아닌 고객 확인이다. 이관은 기술적 완성이 아닌 신뢰의 이전이다.
MODULE 5 — 위기관리
불이 났을 때 어떻게 하는가
위기는 역량을 드러내는 순간이다. 잘 대응한 위기가 가장 강력한 레퍼런스가 된다.
MODULE 6 — 종료 후
프로젝트가 끝나야 진짜 성장이 시작된다
경험은 반추하지 않으면 사라진다. 기록하고 구조화하고 다음 프로젝트에서 써먹는 사람이 성장한다.
SECTION 04
종료 단계 실전 체크리스트
클로징, 하자보수, 개인 성장 준비 항목을 점검하세요
클로징 체크리스트
0 / 8 완료
  • 계약상 완료 조건(기능 구현, 데이터 이관, 문서 전달, 교육) 전항목 충족 여부 확인
  • GR: 연결 마감 전체 사이클 1회 이상 실제 데이터로 완주 확인
  • SAC-P: 계획 수립 사이클 전체 플로우(입력→승인→확정) 완주 확인
  • 고객 인수인계 서명(공식 종료 확인서) 완료
  • 컨설턴트 시스템 접근 권한 회수 또는 하자보수용 최소 권한으로 전환 완료
  • Lessons Learned 문서 작성 완료 (사건-원인-재발방지 세트 기준)
  • 종료 회의 개최 및 미완 항목·하자보수 기간·향후 협력 가능성 공유 완료
  • Phase 2 또는 유지보수 계약 가능성을 내부 영업 파이프라인에 등록
하자보수 & 운영 이관 체크리스트
0 / 6 완료
  • 하자보수 기간(시작일·종료일)과 SLA(Critical 24h, Major 72h)를 계약 또는 서면 합의로 확정
  • 공식 하자 접수 채널(이메일/티켓 시스템) 고객에게 안내 완료
  • 운영 가이드(마감 절차, 에러 대응, 에스컬레이션 연락처) 전달 완료
  • Key User가 독립 실행(마감 사이클 또는 계획 사이클 1회)을 완료하고 확인서 수령
  • 알려진 한계(Workaround 중인 결함, 수작업 항목) 목록을 운영팀에 전달
  • 하자보수 기간 종료 시점에 유지보수 계약 전환 제안 예정일 내부 캘린더에 등록
개인 성장 준비 체크리스트
0 / 5 완료
  • 개인 회고 노트 작성 완료 (처음 알게 된 것 / 실수한 것 / 다음에 다르게 할 것)
  • 레퍼런스 문서 작성 완료 (기밀 익명화 포함: 산업군·규모·핵심 구현·성과 수치)
  • 이번 프로젝트에서 처음 접한 기술·회계 개념을 ASPN 내부 지식 베이스에 기여
  • 다음 프로젝트에서 내가 맡고 싶은 역할과 성장 목표를 PM 또는 리더에게 공유
  • "Beyond Configuration" 관점 점검: 이번 구현이 고객 비즈니스에 어떤 의미인지 한 문장으로 설명할 수 있는가
SECTION 05
확인 문제
각 문항을 읽고 가장 적절한 답을 선택하세요
Q1. 공식 종료(Formal Closure)와 실질 종료(Actual Closure)의 차이를 가장 정확하게 설명한 것은?
① 공식 종료는 Go-Live 완료이고, 실질 종료는 하자보수 기간 종료다.
② 공식 종료는 계약 완료 조건 충족과 서명이고, 실질 종료는 고객이 컨설턴트 없이 시스템을 스스로 운영할 수 있는 상태다.
③ 두 가지는 동일한 의미이며, 고객 사인오프로 동시에 달성된다.
④ 공식 종료는 PM이 선언하고, 실질 종료는 고객이 선언한다.
Q2. 다음 중 하자보수 대상이 아닌 것은?
① Fit-Gap에 합의한 IC 제거 룰이 특정 거래 유형에서 동작하지 않는다.
② 이관 완료 후 검증 중 잔액 불일치 오류가 발견되어 재처리가 필요하다.
③ 인사 이동으로 새로 배정된 Key User가 시스템 사용 교육을 요청한다.
④ 계약 명세에 정의된 리포트 응답 시간(30초 이내)이 지켜지지 않는다.
Q3. 실질적인 Lessons Learned 문서의 특징으로 가장 적절한 것은?
① "커뮤니케이션을 더 강화한다"처럼 원칙 수준의 교훈을 기록한다.
② 프로젝트에서 잘된 점 위주로 기록하여 팀 사기를 높인다.
③ 구체적 사건 → 원인 → 재발 방지 조치를 한 세트로 기록한다.
④ 고객에게 공유하는 문서이므로 내부 실수는 포함하지 않는다.
Q4. 하자보수 기간 중 고객이 "IC 제거 룰에 Fit-Gap에 없던 새로운 거래 유형을 추가해달라"고 요청했다. 올바른 대응은?
① 관계 유지를 위해 무상으로 처리한다.
② 하자보수 기간이므로 모두 처리해야 한다.
③ 즉시 거절하고 별도 계약을 요구한다.
④ Fit-Gap 문서를 확인하여 신규 요청임을 확인한 뒤, 서면으로 하자보수 범위 외임을 통보하고 별도 계약 또는 Phase 2를 제안한다.
Q5. "Beyond Configuration"의 관점에서 컨설턴트가 고객 CFO에게 해야 할 올바른 설명은?
① "IC Elimination Rule을 GR 시스템에 설정 완료했습니다."
② "Transport가 PRD에 반영되어 설정이 완료됐습니다."
③ "ACDOCU 테이블에 연결 데이터가 정상 적재됐습니다."
④ "내부거래 제거 자동화로 연결 마감 시 수작업 오류 리스크가 제거되어 재무제표 신뢰도가 높아졌습니다."
