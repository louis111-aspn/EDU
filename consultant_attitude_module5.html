M2 관계자 각 관계자가 원하는 것과 두려워하는 것을 먼저 파악 리더에게 문제만 들고 가거나, 현업에게 컨설팅 용어 사용 미팅 전 "이 관계자가 가장 원하는 것은?" 자문

M4 문서 채널 선택 → 제목에 액션 유형 → 본문 4단 포맷 메신저로 복잡한 이슈를 처리하거나 결정을 서면화하지 않음 이메일 발송 전 "수신자가 읽고 무엇을 해야 하는지 명확한가?" 확인
M5 드릴 아는 것과 말할 수 있는 것은 다르다 — 소리 내어 연습 이론은 이해했지만 실제 상황에서 구 패턴이 자동으로 나옴 매주 Role-play 1회, 이번 주 실수 1개 기록
컨설턴트 화법의 3층 구조
Layer 1 — Foundation
언어 습관
결론 먼저, 사실/의견 분리, "~인 것 같습니다" 제거. 매일 발화하는 모든 문장에 적용되는 기반.
Layer 2 — Application
관계·상황 적용
관계자 유형별, 미팅 유형별, 채널별로 다르게 적용하는 중간 층. 경험이 쌓일수록 자동화된다.
Layer 3 — Mastery
판단과 영향력
상황을 읽고 먼저 움직인다. 팀과 고객을 이끄는 언어를 사용한다. 가르칠 수 있을 때 완성된다.
성장 원칙: Layer 1이 불안정한 상태에서 Layer 2·3을 시도하면 상황별로 흔들린다. 언어 습관(M1)을 먼저 체화하고, 그 위에 관계·상황 적용(M2·M3·M4)을 쌓는다.
즉시 사용 금지 표현 — 최종 목록

이 표현들이 입에서 나오려는 순간을 포착하는 것이 훈련의 시작이다. 포착하면 멈추고 대체 표현으로 바꾼다.

~인 것 같습니다 ~할 수도 있습니다 검토해보겠습니다 아마 ~일 것입니다 그렇게 된 것 같습니다 좋은 것 같습니다 사실 ~인데요 나름 ~했습니다 어떻게 할까요? 빠른 시일 내에 조금 늦어질 것 같아요 그건 좀 아닌 것 같은데요
대체 원칙: 위 표현이 나오려는 순간 → "내가 왜 확신하지 못하는가?"를 먼저 자문한다. 불확실하면 불확실성의 범위와 이유를 명시한다. 확신이 있으면 근거를 먼저 말하고 결론을 낸다.
Role-play 카드
실제 대화 흐름으로 구성된 Role-play 시나리오. 나쁜 응답과 좋은 응답을 비교하며 왜 다른지를 파악한다. 팀원과 짝을 지어 소리 내어 연습한다.
RP-01
리더에게 일정 지연을 보고하는 상황
▼
상황 설정
데이터 분석 작업이 예상보다 2일 지연될 것으로 파악됐다. 원인은 고객사 데이터 품질 이슈다. 리더에게 주간 보고 미팅에서 이 사실을 알려야 한다.
리더
"이번 주 분석 작업 진행 상황은요?"
❌ 나쁜 응답
"음... 데이터 쪽에 좀 문제가 있어서 생각보다 좀 늦어질 것 같습니다. 최대한 빨리 해볼게요."
문제점
얼마나 늦는지, 왜 늦는지, 어떻게 대응할 건지 — 리더가 판단에 필요한 정보가 하나도 없다. "최대한 빨리"는 약속이 아니다.
✓ 좋은 응답
"현재 분석 3단계 중 2단계까지 완료했습니다. 고객사 데이터에서 중복 항목이 확인되어 정제 작업이 추가로 필요합니다. 원래 금요일 완료 예정이었는데, 다음 주 화요일까지 2일 연장이 필요합니다. 클라이언트 보고 일정에 영향이 있을 수 있어서 방향 확인을 부탁드립니다."
핵심 원리
현황(2/3단계) + 원인(데이터 중복) + 변경 일정(화요일) + 영향(클라이언트 보고) + 결정 요청. 리더가 판단할 수 있는 모든 정보가 포함됐다.
리더
"클라이언트 보고가 다음 주 수요일이니 화요일까지 가능하면 됩니다. 데이터 정제는 혼자 하기 어렵지 않아요?"
✓ 이어서
"충분히 감당 가능합니다. 오늘 오후 정제 기준을 확정하고 내일부터 작업 시작하면 화요일 납품이 가능합니다. 혹시 도움이 필요한 상황이 생기면 미리 말씀드리겠습니다."
Role-play 포인트
이 시나리오에서 연습할 것: ① 수치로 현황 제시 ② 원인을 한 문장으로 ③ 구체적 일정 변경 ④ 영향 범위 언급 ⑤ 결정 요청. 이 5가지가 모두 포함되지 않으면 다시 한 번.
RP-02
고객사 현업이 시스템 변경에 강하게 저항하는 상황
▼
상황 설정
현업 팀장이 새 시스템 도입에 강하게 반발하고 있다. "우리 팀은 지금 방식이 맞습니다. 왜 바꿔야 하죠?"라는 질문을 직접적으로 던지고 있다.
현업
"솔직히 지금 방식이 더 익숙하고 우리한테는 맞습니다. 왜 굳이 바꿔야 하는 건지 모르겠어요."
❌ 나쁜 응답
"다른 회사들도 다 이렇게 전환하고 있습니다. 적응하시면 금방 익숙해지실 겁니다."
문제점
상대의 감정과 논리를 무시했다. "적응하세요"는 존중이 아닌 일방적 통보다. 저항이 강화된다.
✓ 좋은 응답
"충분히 이해됩니다. 지금 방식으로 오랫동안 운영해오셨는데 바꾸자고 하면 당연히 의문이 드실 겁니다. 말씀하신 '지금 방식이 맞다'는 부분에서, 구체적으로 어떤 점이 지금 방식에서 잘 작동하고 있는지 여쭤봐도 될까요? 그 부분을 지키면서 개선할 수 있는 방향을 찾고 싶습니다."
현업
"우리 팀만의 예외 케이스가 많아요. 시스템이 그걸 못 따라와요."
✓ 이어서
"중요한 말씀입니다. 그 예외 케이스들이 구체적으로 어떤 상황인지 알아야 설계에 반영할 수 있습니다. 가장 자주 발생하는 예외 케이스 두세 가지를 예시로 설명해주시겠어요? 이것이 시스템에서 처리가 가능한지 직접 확인해드리겠습니다."
Role-play 포인트
공감 → 이해를 위한 질문 → 구체적 대안 탐색의 흐름. "적응하세요"나 "다른 회사도 다 해요"가 나오면 실패. 상대가 말할수록 정보가 쌓이고 해결책이 보인다.
RP-03
경영진 보고 중 예상치 못한 반론을 받은 상황
▼
상황 설정
경영진에게 시장 진입 전략을 보고하는 중이다. 핵심 결론은 "A 시장 진입을 권고한다"였는데, 부사장이 예상치 못한 반론을 제기했다.
부사장
"A 시장이 성장한다는 건 알겠는데, 우리 회사 역량으로 그 시장에서 경쟁이 가능한지 의문입니다. 경쟁사 B가 이미 강자로 자리잡은 시장 아닙니까?"
❌ 나쁜 응답
"아, 사실 저도 그 부분이 좀 걱정이 되긴 했는데요... 데이터를 다시 한번 살펴봐야 할 것 같습니다."
문제점
자신감이 무너지고 결론 자체가 흔들린다. 경영진은 이 순간 "이 분석을 믿어도 되는가?"를 의심하기 시작한다.
✓ 좋은 응답
"좋은 포인트입니다. 경쟁사 B의 포지션을 저희도 분석에 반영했습니다. B사는 프리미엄 세그먼트에 집중하고 있고, 저희가 권고드리는 진입 포인트는 중소형 고객군입니다. 이 세그먼트에서 B사의 점유율은 현재 12%로, 경쟁 강도가 상대적으로 낮습니다. 다만 부사장님께서 '역량'을 언급하셨는데, 어떤 부분의 역량이 특히 우려되시는지 말씀해주시면 해당 부분 데이터를 추가로 검토해드리겠습니다."
부사장
"주로 영업 네트워크가 없다는 점이 걱정입니다."
✓ 이어서
"정확히 짚어주셨습니다. 이 부분은 파트너십 전략으로 보완하는 방안을 검토했으며, 슬라이드 8페이지에 3가지 파트너 옵션이 있습니다. 보고 후 이 부분을 별도로 심화 분석하여 공유드리겠습니다."
Role-play 포인트
반론 = 추가 정보 요청. "좋은 포인트" → 기존 분석 근거 제시 → 상대 우려의 구체화 요청 → 해결 방향 제시. 자신감을 유지하면서도 열린 자세를 보여주는 것이 핵심.
RP-04
팀원에게 작업물 피드백을 주는 상황
▼
상황 설정
팀원이 작성한 슬라이드를 검토했다. 논리 흐름에 문제가 있고, 데이터 근거가 부족한 슬라이드가 두 장 있다. 팀원은 열심히 했고 기대를 갖고 있다.
❌ 나쁜 피드백
"전체적으로 좀 약한 것 같아요. 논리가 부족하고, 데이터도 더 보강해야 할 것 같습니다. 다시 해주세요."
문제점
"좀 약한 것 같다"는 피드백이 아니다. 어디가, 왜 약한지, 어떻게 고쳐야 하는지가 없다. 팀원은 무엇을 해야 할지 모른다.
✓ 좋은 피드백
"전체 흐름은 잘 잡혔습니다. 특히 첫 세 슬라이드의 문제 정의 부분은 명확합니다. 두 가지 구체적인 피드백이 있습니다. 첫째, 5번 슬라이드에서 '경쟁사 대비 우위'를 주장하는데 뒷받침하는 수치가 없습니다. 경쟁사 비교 데이터를 추가해주시면 설득력이 높아집니다. 둘째, 7번 슬라이드의 Action Title이 사실 기술에 가깝습니다. '~함으로써 ~를 달성할 수 있음' 형식의 결론 문장으로 바꾸면 어떨까요?"
팀원
"5번 슬라이드 데이터는 어디서 구하면 좋을까요?"
✓ 이어서
"고객사에서 받은 업계 보고서 파일에 경쟁사별 점유율 데이터가 있습니다. 공유 폴더 /data/industry에 있어요. 내일 오전까지 수정본을 보내주면 오후 리뷰 전에 확인하겠습니다."
Role-play 포인트
잘된 것 먼저 → 구체적 이슈 (슬라이드 번호 + 무엇이 + 왜 문제인지) → 개선 방향 제시 → 다음 단계. 피드백은 사람이 아니라 작업물에 대한 것임을 유지한다.
Role-play 활용법: 혼자 읽지 말고 팀원과 역할을 나눠 소리 내어 연습한다. 녹음하여 들으면 본인도 몰랐던 패턴(말 끝 흐리기, 반복 표현 등)을 발견할 수 있다. 한 시나리오당 최소 3회 반복 권장.
어구 교체 훈련
나쁜 표현을 발견하는 것만으로는 부족하다. 즉시 대체 표현이 나와야 현장에서 쓸 수 있다. 왼쪽의 금지 표현을 보고 오른쪽 표현을 소리 내어 말하는 연습을 한다.
모호함 제거 — 불확실성 표현
❌ 금지 표현 ✓ 대체 표현 전환 이유
"~인 것 같습니다" "X 데이터 기준으로 A입니다" / "제 판단으로는 A입니다 — 근거는 X입니다" 사실이면 단언, 판단이면 근거를 붙인다
"아마 ~일 것입니다" "현재 확인된 범위에서는 A입니다. B 부분은 [날짜]까지 확인하겠습니다" 추정과 확인 예정을 분리하여 신뢰를 유지
"검토해보겠습니다" "[날짜 시간]까지 확인하여 [채널]로 공유드리겠습니다" 기한과 채널이 없는 약속은 약속이 아니다
"빠른 시일 내에" "오늘 오후 5시까지" / "다음 주 화요일 오전까지" 구체적 기한이 있어야 상대가 계획할 수 있다
"좋은 것 같습니다" "A 이유로 이 방향이 타당합니다" / "X 기준에서 B안이 적합합니다" 평가에는 반드시 기준이 있어야 한다
책임 회피 제거 — 수동태·모호한 주어
❌ 금지 표현 ✓ 대체 표현 전환 이유
"그렇게 된 것 같습니다" "제가 X 단계에서 Y를 확인하지 않아 이 오류가 발생했습니다" 책임을 명확히 하면 오히려 신뢰가 쌓인다

Q01 — Module 1. 마인드셋
리더에게 분석 결과를 보고할 때 "이 시장은 성장 중이고, 진입하면 승산이 있을 것 같습니다"라고 말했다. 이 발언의 핵심 문제는?
A수치가 없다
B사실과 의견이 혼용되어 있고, 의견에 근거가 없다
C문장이 너무 짧다
D리더에게 직접 말하면 안 된다
"시장은 성장 중"은 사실일 수 있지만, "승산이 있을 것 같습니다"는 의견이며 근거가 없다. 컨설턴트는 사실과 의견을 분리하고, 의견에는 반드시 근거를 붙여야 한다. 수치가 없는 것도 문제지만, 본질은 사실/의견 혼용이다.
Q02 — Module 1. 마인드셋
No Surprise 원칙이란 무엇인가?
A클라이언트에게 예상치 못한 분석 결과를 보여주지 않는 것
B미팅에서 아젠다 외 주제를 꺼내지 않는 것
C리더나 클라이언트가 나보다 먼저 이슈를 발견하는 상황을 만들지 않는 것
D보고서에 새로운 내용을 넣지 않는 것
No Surprise 원칙의 핵심은 이슈 발견→보고까지의 시간을 최소화하는 것이다. 리더나 클라이언트가 나보다 먼저 문제를 발견하면 신뢰가 즉시 손상된다. 이슈를 혼자 해결하려다 늦게 알리는 것이 가장 위험한 패턴이다.
Q03 — Module 2. 관계자
고객사 현업 담당자가 "왜 이걸 해야 하죠?"라고 저항할 때 가장 적절한 첫 반응은?
A"위에서 결정된 사항입니다"
B데이터를 꺼내어 효과를 수치로 설명한다
C의문을 공감하고, "구체적으로 어떤 부분이 걱정되십니까?"라고 질문한다
D"다른 회사들도 다 이렇게 합니다"라고 설득한다
현업의 저항은 정보다. 저항 이면에 있는 실제 우려를 파악하기 전에 논리나 데이터로 설득하려 하면 표면적 동의만 얻게 된다. 먼저 공감하고, 구체적인 우려를 질문으로 끌어내는 것이 첫 단계다.
Q04 — Module 2. 관계자
협력사에 요구사항을 전달할 때 올바른 순서는?
A요구사항 → 기한 → 배경
B맥락(Why) → 요구사항(What) → 조건·제약(Constraint)
C결론 → 요구사항 → 맥락
D기한 → 요구사항 → 배경
협력사에 맥락(Why) 없이 요구(What)만 전달하면 반발을 부른다. 맥락을 먼저 공유하면 파트너가 요청의 배경을 이해하고 더 능동적으로 대응한다. 조건·제약(Constraint)을 함께 전달하면 나중에 "그 조건이 있었어요?"를 방지한다.
Q05 — Module 3. 미팅
이슈 해결 미팅에서 가장 먼저 해야 하는 것은?
A솔루션을 브레인스토밍한다
B책임자를 먼저 확인한다
C참석자 전원이 같은 문제를 보고 있는지 문제 정의를 합의한다
D과거 유사 사례를 찾아본다
이슈 해결 미팅에서 가장 많은 시간이 낭비되는 이유는 문제 정의 없이 솔루션 경쟁으로 직행하기 때문이다. 문제 정의에 5분을 투자하면 나머지 55분을 아낄 수 있다. 각자가 다른 문제를 보고 있으면 어떤 솔루션도 효과가 없다.
Q06 — Module 3. 미팅
경영진 보고에서 반론을 받았을 때 올바른 첫 반응은?
A"저희가 충분히 검토한 내용입니다"라며 방어한다
B"사실 저도 그 부분이 걱정됐는데요"라며 공감을 표한다
C"좋은 포인트입니다"로 수용하고, 분석의 근거와 가정을 설명한다
D즉시 슬라이드를 추가 설명으로 보완한다
경영진의 반론은 공격이 아니라 추가 정보나 관점이다. "좋은 포인트입니다"는 방어를 해제하고 협력적 대화를 여는 언어적 장치다. 이후 기존 분석의 근거와 가정을 설명하고, 상대의 우려를 구체화하는 질문으로 이어간다. 자신감을 잃거나 즉각 양보하는 것 모두 좋지 않다.
Q07 — Module 4. 이메일
이메일 제목으로 가장 적절한 것은? (상황: 벤더 선정 결정 요청)
A"벤더 관련 문의드립니다"
B"중요한 건이 있어서요"
C"[의사결정 요청] 벤더 최종 선정 — A사·B사 비교 및 권고안 / 5/17(금)까지"
D"벤더 A와 B 중 선택해주시면 감사하겠습니다"
좋은 이메일 제목은 ① 액션 유형 [의사결정 요청], ② 주제(벤더 선정), ③ 핵심 내용(비교+권고안), ④ 기한(5/17)을 포함한다. 수신자는 제목만 보고 어떤 액션을 언제까지 해야 하는지 알아야 한다.
Q08 — Module 4. 메신저
메신저에서 복잡한 이슈를 논의하여 결론이 났다. 다음 단계로 가장 올바른 행동은?
A결론이 났으니 바로 실행을 시작한다
B즉시 이메일로 논의 요약과 결정 사항을 서면 확인한다
C메신저 캡처를 저장해둔다
D다음 주 회의에서 다시 확인한다
메신저의 결론은 서면화될 때 비로소 공식 합의가 된다. 메신저 기록은 분산되고 맥락이 유실되기 쉽다. 논의 후 즉시 이메일로 요약을 보내면 모든 참여자가 같은 이해를 갖게 되고, 나중의 "그때 그렇게 결정했나요?"를 방지한다.
Q09 — Module 4. 회의록
좋은 회의록의 액션 아이템에 반드시 포함되어야 하는 3가지는?
A배경 / 요청 내용 / 기한
B액션 내용(What) / 담당자(Owner) / 기한(Due Date)
C담당자 / 우선순위 / 관련 부서
D문제 원인 / 담당자 / 검토 일정
액션 아이템의 3종 세트: ① 무엇을(What) ② 누가(Owner) ③ 언제까지(Due Date). 이 세 가지 중 하나라도 빠지면 실행이 지연되거나 책임 소재가 불명확해진다. "검토 필요" 또는 "추후 진행"은 액션 아이템이 아니다.
Q10 — 종합
컨설턴트가 미팅 중 모르는 질문을 받았을 때 가장 올바른 대응은?
A"아마 X 정도 될 것 같습니다"라며 즉흥 추정으로 답한다
B침묵으로 넘어간다
C"제 담당 범위가 아닙니다"라고 말한다
D"현재 확인된 범위에서는 X입니다. Y 부분은 오늘 중으로 확인하여 공유드리겠습니다"라고 답한다
추측으로 답하면 나중에 틀렸을 때 전체 분석의 신뢰도가 흔들린다. 모르는 것을 모른다고 하되, 아는 것의 범위를 명확히 하고, 확인 기한과 채널을 구체적으로 제시하면 신뢰가 오히려 높아진다. "모른다"와 "확인하겠다"는 다르다.

월간 루틴 — 가르침으로 완성하기
왜 가르쳐야 하는가

지식을 설명할 수 있을 때 비로소 자신의 것이 된다. 이것을 '프로테제 효과(Protégé Effect)'라 한다.

팀원이나 후배에게 이 원칙을 설명하는 과정에서 본인이 모호하게 알고 있던 부분이 드러나고, 더 깊이 이해하게 된다.

월간 루틴 3가지

① 팀 내 원칙 공유: 월 1회 팀 미팅에서 이 시리즈 중 하나의 원칙을 5분 안에 설명한다.

② 신규 팀원 온보딩: 새로운 팀원에게 이 시리즈 모듈 1~2를 먼저 소개한다.

③ 자기 평가 리뷰: 지난 한 달 학습 로그를 읽고, 가장 많이 개선된 것과 아직 남은 것을 정리한다.

최종 종합 체크리스트
5개 모듈 전체에서 가장 중요한 항목을 한자리에 모았다. 이 체크리스트가 70% 이상 체크되어야 현장에서 원칙을 적용하고 있다고 볼 수 있다.
