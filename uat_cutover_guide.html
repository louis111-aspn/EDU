SECTION 01
UAT 개요
UAT는 무엇이고 무엇이 아닌가 — 진입 조건과 실패 원인
UAT의 정의 — "고객 확인"이지 "버그 발견"이 아니다

UAT(User Acceptance Test, 사용자 수락 테스트)는 고객이 업무 시나리오 기반으로 시스템이 요구사항대로 동작하는지 최종 확인하는 단계입니다. UAT는 컨설턴트가 아닌 고객이 직접 실행합니다.

UAT에서 기본적인 오류가 대량으로 발견된다는 것은 단위 테스트·통합 테스트가 충분하지 않았다는 신호입니다. 그 신호가 고객에게 직접 노출되는 것이 문제입니다.

✗ UAT가 아닌 것

시스템 버그를 처음 발견하는 자리

컨설턴트가 고객 앞에서 기능을 처음 시연하는 자리

요구사항을 다시 협의하는 자리

범위에 없는 기능을 추가 요청하는 자리

✓ UAT가 맞는 것

사전에 합의된 시나리오를 고객이 직접 실행해 결과를 확인하는 자리

발견된 결함을 분류·기록하고 Go-Live 가능 여부를 판단하는 자리

고객이 시스템을 인수할 준비가 되었는지 확인하는 자리

UAT 실패의 공통 원인

UAT가 계획대로 진행되지 않는 경우의 원인은 대부분 UAT 이전 단계에서 만들어집니다.

#실패 원인이전 단계 연결예방
1 단위·통합 테스트 불충분 → 기본 오류 대량 발견 Implementation 단계 단위 테스트 미흡 UAT 진입 조건에 단위 테스트 Pass 필수 포함
2 고객 담당자가 시나리오를 이해 못 함 시나리오 사전 교육 없음 UAT 시작 전 시나리오 워크숍 1회 필수
3 테스트 데이터가 실제 업무와 다름 테스트 데이터 준비 부족 실제 업무 데이터 기반 테스트 환경 사전 구성
4 UAT 중 범위 외 요청 빈발 → 일정 초과 Fit-Gap·CR 관리 불충분 UAT 범위 명시, 추가 요청은 Post Go-Live 백로그로 이관
5 고객 담당자 참석률 저조 Kick-off에서 UAT 참석 합의 미비 UAT 일정·참석자·역할을 Kick-off에서 사전 합의
방법론별 UAT 진입 조건
GR — Realization 완료 후

• 모든 Configuration 단위 테스트 Pass 완료

• Enhancement(개발) 단위 테스트 Pass 완료

• 통합 테스트 완료 — 연결 마감 End-to-End 흐름 검증

• QAS 환경에 최신 Transport 반영 확인

• UAT 시나리오 문서 고객 사전 배포 완료

• 테스트 데이터(법인별 잔액, 내부거래 전표) 구성 완료

SAC-P — 최종 Sprint 완료 후

• 모든 Sprint 백로그 완료(Done) 확인

• Data Action 단위 테스트 Pass 완료

• Story·보고서 실제 데이터 기반 검증 완료

• 실적 데이터 연동(Live/Import) 정상 동작 확인

• UAT 시나리오 — 계획 수립 사이클 전체 흐름 기반 작성 완료

• 고객 담당자(LOB별) UAT 참석 일정 확정

⚠ UAT 진입 판단

진입 조건이 하나라도 미충족이면 UAT를 시작하지 않습니다. 미완성 상태로 UAT를 진행하면 고객의 신뢰가 떨어지고, 결함 수가 폭발적으로 증가해 오히려 일정이 더 늦어집니다. "일단 시작하고 고치자"는 전략은 UAT에서 통하지 않습니다.

SECTION 02
UAT 시나리오 설계
업무 흐름 기반 시나리오 — 기능 테스트가 아닌 프로세스 테스트
시나리오 작성 원칙 — 기능 단위가 아닌 업무 흐름 단위

UAT 시나리오의 가장 흔한 실수는 기능 단위로 작성하는 것입니다. "ICMR 실행 화면에서 버튼을 누르면 대사가 실행된다"는 기능 테스트이지 UAT가 아닙니다. UAT 시나리오는 업무 흐름(End-to-End) 기반이어야 합니다.

✗ 기능 단위 시나리오

TC-01: ICMR 실행 버튼 클릭 시 대사가 실행된다

TC-02: FS Item 보고서 화면이 열린다

TC-03: 투자자본상계 버튼이 동작한다

→ 각 기능은 동작해도 전체 마감 프로세스가 맞는지 알 수 없음

✓ 업무 흐름 시나리오

SC-01: 법인 A·B 전표 입력 → ICMR 대사 → 차이 조정 → 투자자본상계 → 연결 재무제표 생성 → 수치 검증

→ 실제 월 마감 프로세스를 처음부터 끝까지 한 번에 검증

시나리오 설계 원칙 3가지

업무 완결성: 각 시나리오는 업무적으로 의미 있는 결과(재무제표, 계획 보고서 등)까지 도달해야 함

실제 데이터: 테스트 전용 더미 데이터가 아닌 실제 업무와 동일한 구조의 데이터 사용

고객이 직접 실행: 컨설턴트가 시연하는 것이 아니라 고객 담당자가 직접 실행할 수 있도록 단계별 절차 명시

GR — 연결 마감 UAT 시나리오 구성

GR UAT의 핵심은 월 마감 End-to-End 흐름을 검증하는 것입니다. 개별 기능이 아닌 마감 프로세스 전체가 정확히 동작하는지 확인합니다.

시나리오업무 흐름검증 기준
SC-GR-01
내부거래 대사		 법인별 개별 데이터 제출 → ICMR 실행 → 차이 확인 → 조정 → 재대사 대사 완료 후 미조정 잔액 허용 한도 이내, 조정 분개 정확성
SC-GR-02
투자자본상계		 지분 구조 입력 → C/I 실행 → 연결 자본 확인 투자주식·자본 상계 후 이중 계상 없음, 소수주주지분 정확 계산
SC-GR-03
지분법 평가		 관계사 당기순이익 입력 → 지분법 실행 → 연결 손익 반영 확인 지분법이익/손실 지분율 기준 정확 반영, 손실 중단 케이스 포함
SC-GR-04
외화 환산		 외화 법인 데이터 입력 → 환산 실행 → KRW 환산 재무제표 확인 환산 금액 정확성, 환산차이 OCI 반영, 환율 소스 정확성
SC-GR-05
연결 재무제표		 전 시나리오 완료 후 연결 재무제표(B/S·I/S·C/F) 생성 개별 법인 합계 = 연결 금액 + 조정 항목, IFRS 기준 표시 정확성
추가 시나리오 고려 항목

IFRS 18 적용 대상인 경우: 영업·투자·재무 카테고리 분류 보고 시나리오 추가. BPC에서 GR로 마이그레이션된 경우: 동일 기간 BPC 결과값과 GR 결과값 대조 시나리오 필수.

SAC-P — 계획 수립 사이클 UAT 시나리오 구성

SAC-P UAT의 핵심은 계획 수립 전체 사이클이 실제 업무 방식대로 동작하는지 검증하는 것입니다.

시나리오업무 흐름검증 기준
SC-SP-01
Bottom-Up 비용 계획		 LOB 담당자 비용 직접 입력 → 법인 집계 → 그룹 집계 확인 입력값 = 집계값, 담당자별 입력 권한 정상 동작
SC-SP-02
Top-Down 목표 배분		 그룹 목표 입력 → Data Action 배분 실행 → LOB별 배분 확인 배분 합계 = 입력 목표, 배분 기준(드라이버) 정확 적용
SC-SP-03
실적 연동 확인		 S/4HANA 실적 데이터 갱신 → SAC 반영 확인 → 계획-실적 대비 실적값 정확성, 갱신 주기 정상 동작, 계획-실적 차이 계산 정확성
SC-SP-04
시나리오 분석		 Base 버전 복사 → 시나리오 가정 변경 → 손익 시뮬레이션 버전 복사 정확성, 원본 버전 불변, 시뮬레이션 결과 논리 일치
SC-SP-05
경영 보고서		 계획 수립 완료 후 경영 보고 Story 실행 → 수치 검증 보고서 수치 = 모델 데이터, 드릴다운 정상 동작, 출력 형식
시나리오 커버리지 관리

시나리오 수는 많다고 좋은 것이 아닙니다. 핵심 업무 흐름을 빠짐없이 커버하되, 중복을 제거해야 합니다. 커버리지 관리를 위해 요구사항 추적 매트릭스(RTM)를 활용합니다.

RTM (요구사항 추적 매트릭스) 최소 구성

열 구성: 요구사항 ID → Fit-Gap ID → 구현 항목 → UAT 시나리오 ID → 테스트 결과

목적: 모든 요구사항이 최소 하나의 UAT 시나리오로 검증되는지 확인

커버리지 기준: Critical 요구사항 100% / Major 요구사항 90% 이상 / Minor 요구사항 70% 이상

상황: GR 프로젝트에서 기능별로 시나리오를 작성하다 보니 총 120개가 되었습니다. 계획한 UAT 기간(2주) 내에 절반도 완료하지 못했고 Go-Live 일정이 3주 지연되었습니다.

원인: 업무 흐름이 아닌 기능 단위로 시나리오를 작성해 중복이 많았습니다. 또한 고객 담당자가 전체 시나리오를 소화할 시간이 없었습니다.

해결: 시나리오를 업무 흐름 기반으로 재구성하니 핵심 시나리오 15개로 줄었습니다. 각 시나리오가 End-to-End 흐름을 커버하므로 커버리지는 오히려 높아졌습니다. UAT는 1주 내에 완료되었습니다.

SECTION 03
결함 분류 기준과 처리
Critical · Major · Minor — 그리고 Go-Live 판단 기준
결함 분류 기준 — 3단계

UAT에서 발견된 결함을 모두 동일하게 처리하면 시간이 부족해집니다. 결함을 업무 영향도 기준으로 분류하고 우선순위를 부여해야 합니다.

🔴 Critical

정의: 핵심 업무 프로세스가 완전히 중단됨. 우회 방법(Workaround) 없음.

예시(GR): 연결 마감 실행 시 오류로 재무제표 생성 불가

예시(SAC-P): 계획 데이터 저장 불가, 실적 연동 전면 실패

Go-Live: Critical 결함이 하나라도 미해결이면 Go-Live 불가

🟡 Major

정의: 중요 기능이 부분적으로 동작하지 않음. 임시 우회 방법은 존재.

예시(GR): 특정 법인의 환산 금액 오차 발생 (수동 조정 가능)

예시(SAC-P): 일부 드릴다운 동작 오류 (상위 집계는 정상)

Go-Live: 수정 계획 및 우회 방법 합의 시 조건부 Go-Live 가능

🟢 Minor

정의: 업무에 실질적 영향 없는 UI/표시 오류, 편의성 문제.

예시(GR): 보고서 컬럼 순서 다름, 레이블 오타

예시(SAC-P): 차트 색상 다름, 숫자 포맷 설정 차이

Go-Live: Post Go-Live 패치로 처리 합의 후 Go-Live 가능

⚠ 분류 기준은 반드시 사전 합의

결함 분류 기준을 UAT 전에 고객과 서면으로 합의해야 합니다. 합의 없이 UAT를 시작하면 고객은 모든 결함을 Critical로 주장하고, 컨설턴트는 Minor라고 주장하는 상황이 발생합니다. 분류 기준 자체가 협상 대상이 되면 UAT 진행이 마비됩니다.

단계책임자실전 주의점
발견·기록 고객 UAT 담당자 결함 로그에 재현 단계(Steps to Reproduce)를 반드시 포함. "안 된다"는 기록은 수정 불가
분류 컨설턴트 + 고객 공동 사전 합의된 기준으로 즉시 분류. 분류 이견은 당일 해소 원칙
수정 컨설턴트 Critical은 24시간 내 수정 목표. 수정 후 DEV→QAS Transport 완료 확인
재검증 고객 UAT 담당자 최초 발견자가 직접 재검증. 다른 담당자가 확인하면 원래 문제 재현 여부 불확실
Close 고객 Close는 반드시 고객이 결함 로그에 서명(또는 이메일 확인). 컨설턴트가 일방적으로 Close 불가
Go-Live 판단 기준 — 언제 오픈할 수 있는가

Go-Live는 "모든 결함이 0개일 때"가 아닙니다. 현실적으로 Minor 결함이 남아 있어도 Go-Live를 진행합니다. 중요한 것은 합의된 기준에 따라 판단하는 것입니다.

✓ Go-Live 가능 조건 (예시)

필수: Critical 결함 = 0개

필수: Major 결함 — 모든 항목에 대해 수정 완료 또는 우회 방법·수정 일정 서면 합의

권고: Minor 결함 — Post Go-Live 패치 계획 수립 후 Go-Live 가능

필수: Cutover 리허설 최소 1회 완료

필수: 고객 측 Go-Live 승인 서명 수령

⚠ Go-Live 연기 판단

Critical 결함이 해소되지 않은 상태에서 일정 압박을 이유로 Go-Live를 강행하면, 운영 중 장애로 이어집니다. 이 경우 컨설턴트가 전적인 책임을 지게 됩니다. Go-Live 연기는 치명적이 아닙니다 — 운영 장애가 치명적입니다.

상황: GR 프로젝트에서 특정 법인의 ICMR 대사가 정상 동작하지 않는 Critical 결함이 있었습니다. 고객 임원이 일정상 이유로 Go-Live를 강행했습니다.

결과: Go-Live 후 첫 월 마감 시 해당 법인의 내부거래 대사가 전혀 되지 않아 연결 재무제표 작성이 불가능해졌습니다. 긴급 패치 및 재마감에 1주일이 소요되었고, 해당 기간의 재무 보고가 전면 지연되었습니다.

교훈: Go-Live 판단은 컨설턴트가 명확한 기준을 제시하고 고객이 결정해야 합니다. "일정 때문에 Go-Live 해야 한다"는 고객 요청에는 Critical 결함의 업무 영향을 서면으로 명시하고, 강행 시 책임 소재를 문서화해야 합니다.

SECTION 04
이관(Cutover) 실전
Cutover 계획 · 데이터 적재 · 리허설 · Go-Live 판단
Cutover란 무엇인가

Cutover는 기존 시스템(Legacy·BPC·Excel)에서 새 시스템(GR·SAC-P)으로 업무와 데이터를 공식 전환하는 작업입니다. Cutover가 완료되는 순간부터 새 시스템이 공식 운영 환경이 됩니다.

Cutover는 단순한 "시스템 오픈"이 아닙니다. 데이터 적재, 검증, 구 시스템 종료, 신 시스템 오픈의 전체 절차를 시간 단위로 계획해야 합니다.

Cutover 계획 필수 구성 요소

Task 목록: Cutover 중 수행할 모든 작업을 순서대로 나열

담당자: 각 Task의 실행 책임자 (컨설턴트·고객 구분)

예상 소요 시간: 각 Task의 시작·완료 시간 (분 단위)

의존성: 선행 Task 완료 후에만 시작 가능한 Task 명시

롤백 기준: 어떤 상황에서 Cutover를 중단하고 원복할 것인가

Go/No-Go 체크포인트: 각 단계 완료 후 계속 진행 여부 판단 시점

방법론별 데이터 적재
GR — 초기 잔액·이관 데이터

적재 대상:

• 개별 법인 GL 잔액 (Go-Live 기준일 기준)

• 지분 구조 데이터 (투자주식·취득원가)

• 과거 연결 조정 이력 (필요 시)

• 환율 데이터

검증 방법:

• 적재 후 개별 법인 잔액 합계 = Legacy 시스템 잔액

• 연결 시뮬레이션 실행 → BPC/Excel 결과와 대조

적재 시점: Go-Live 직전 영업 마감 후 (데이터 변동 방지)

SAC-P — 히스토리·실적 데이터

적재 대상:

• 과거 N개년 실적 데이터 (비교 분석용)

• 기존 Excel 계획 데이터 (이관 동의 시)

• 마스터 데이터 (조직·제품·계정 차원)

검증 방법:

• 적재 후 연도별 합계 = 원천 데이터 합계

• 마스터 계층 구조 정확성 확인

• Live Connection 연동 시 S/4HANA 원천과 대조

주의: 히스토리 데이터 범위(연수)는 고객과 사전 합의

Cutover 리허설 — 왜 반드시 필요한가

Cutover 리허설은 실제 Go-Live 전에 Cutover 절차 전체를 실제 환경과 동일한 조건으로 사전 연습하는 것입니다. 리허설 없이 Go-Live를 진행하면 예상치 못한 문제가 발생했을 때 대응 시간이 부족해집니다.

리허설 목적확인 항목
시간 검증 계획한 소요 시간과 실제 소요 시간 차이 확인. 초과 구간 식별 및 대안 준비
데이터 적재 검증 실제 데이터로 적재 스크립트 실행 → 오류 사전 발견 및 수정
역할·책임 검증 각 Task 담당자가 자신의 역할을 명확히 인지하고 있는지 확인
롤백 절차 검증 문제 발생 시 롤백 절차가 실제로 동작하는지 사전 테스트
Go/No-Go 기준 확인 각 체크포인트에서 담당자가 판단 기준을 명확히 이해하고 있는지 확인
리허설 최소 횟수

GR: 최소 1회, 권장 2회. 첫 번째 리허설에서 발견된 문제 수정 후 두 번째 리허설로 검증.

SAC-P: 최소 1회. 데이터 적재 볼륨이 크거나 복잡한 경우 2회 권장.

⚠ Cutover 중 절대 금지

데이터 적재 중 Legacy 시스템 계속 사용: 데이터 불일치 발생. Legacy는 Cutover 시작과 동시에 Read-Only 또는 잠금 상태로 전환.

검증 생략 후 Go-Live 진행: 적재 데이터 오류가 운영 환경에 반영됨. 검증 소요 시간을 Cutover 계획에 충분히 반영해야 함.

롤백 계획 없는 Go-Live: 문제 발생 시 원복 방법이 없으면 더 큰 혼란이 발생. 롤백 기준과 절차를 사전에 문서화.

확인 문제
핵심 개념 이해도 점검
Q1. UAT의 올바른 정의는?
① 컨설턴트가 시스템 버그를 최종 발견하는 단계
② 고객 앞에서 기능을 처음 시연하고 피드백을 받는 단계
③ 고객이 사전 합의된 업무 시나리오를 직접 실행해 시스템이 요구사항대로 동작하는지 최종 확인하는 단계
④ 요구사항을 재협의하고 추가 기능을 결정하는 단계
Q2. UAT 시나리오를 업무 흐름(End-to-End) 기반으로 설계해야 하는 이유는?
① 시나리오 수를 최대화해 커버리지를 높이기 위해
② 고객이 기술적 지식 없이도 시나리오를 작성할 수 있게 하기 위해
③ 개별 기능이 동작해도 전체 마감/계획 프로세스가 올바른지는 End-to-End로만 검증 가능하기 때문
④ 시나리오 작성 시간을 단축하기 위해
Q3. Critical 결함의 정의와 Go-Live 기준으로 올바른 것은?
① 수정에 오래 걸리는 결함 — 수정 계획 합의 시 Go-Live 가능
② 핵심 업무 프로세스가 완전히 중단되며 우회 방법 없는 결함 — 반드시 해소 후 Go-Live
③ 고객이 불만을 표시한 결함 — 고객 승인 시 Go-Live 가능
④ 화면 표시 오류 — Post Go-Live 패치로 처리 가능
Q4. 결함 Close 처리 시 반드시 지켜야 할 원칙은?
① 컨설턴트가 수정 완료 후 자체적으로 Close 처리
② 프로젝트 PM이 검토 후 Close 결정
③ 최초 발견자인 고객 담당자가 직접 재검증 후 Close 확인
④ 수정 후 24시간이 경과하면 자동 Close
Q5. Cutover 리허설이 반드시 필요한 가장 중요한 이유는?
① 고객에게 프로젝트 진행 상황을 보여주기 위해
② 계약서의 마일스톤 조건을 충족하기 위해
③ 실제 소요 시간·오류·역할 불명확 등의 문제를 Go-Live 전에 발견하고 수정하기 위해
④ 데이터 적재량을 사전에 파악하기 위해
