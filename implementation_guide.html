SECTION 01
Implementation 실행 구조 개요
GR Realization과 SAC-P Sprint — 무엇이 같고 무엇이 다른가
두 방법론의 Implementation 흐름 비교

GR(Waterfall/Gate)과 SAC-P(Agile/Sprint)는 구현 단계의 실행 리듬이 근본적으로 다릅니다. 어느 방법론이든 컨설턴트가 해야 할 일의 본질은 같지만, 관리 방식과 산출물 형태가 달라집니다.

GR — Realization Phase

흐름: Fit-Gap 확정 → 설계 문서 작성 → Configuration → Enhancement 개발 → 단위 테스트 → Gate 통과 → UAT 준비

리듬: Phase 단위 — 단계 완료 후 다음 단계로 순차 진행. Gate 기준 충족 시 다음 Phase로 이동.

산출물: Blueprint 문서, Configuration Guide, 개발 사양서(Functional Spec), 단위 테스트 결과서

리스크 지점: Phase 중반에 설계 변경 시 이후 전체 일정에 연쇄 영향

SAC-P — Sprint 실행

흐름: Sprint 계획 → 개발(Data Action·Story·모델) → 데일리 스탠드업 → Sprint 리뷰(고객 시연) → 회고 → 다음 Sprint

리듬: Sprint 단위(1~2주) — 각 Sprint마다 동작하는 결과물을 고객에게 시연. 피드백 즉시 반영.

산출물: Sprint 백로그, 완료된 기능(Done), 리뷰 회의록, 회고 액션 아이템

리스크 지점: 백로그 무한 확장, 스프린트 내 완료 실패 누적

두 방법론의 공통 원칙

방법론이 달라도 Implementation 단계에서 컨설턴트가 지켜야 할 원칙은 동일합니다.

원칙내용위반 시 결과
변경 이력 관리 모든 설정·개발 변경은 기록. "언제, 누가, 왜 바꿨는가"가 항상 추적 가능해야 함 문제 발생 시 원인 추적 불가, 롤백 불가
테스트 후 진행 단위 테스트 없이 다음 작업으로 넘어가지 않음. 검증되지 않은 기능 위에 기능을 쌓지 않음 하류 단계에서 결함 폭증, UAT 실패
고객 가시성 확보 구현 진행 상황을 고객이 항상 볼 수 있게 유지. 블랙박스 구현 금지 기대치 불일치 → 인도 직전 대규모 재작업
범위 통제 합의된 범위 외 작업은 공식 CR 없이 시작하지 않음 공수 초과, 일정 지연, 클레임 발생
GR Realization — Phase 진행 기준(Gate)

SAP Activate 기반 GR 프로젝트에서 각 Phase는 Gate 기준을 충족해야 다음 단계로 이동할 수 있습니다. Gate를 형식적으로 통과시키면 다음 Phase에서 문제가 증폭됩니다.

⚠ Realization 진입 조건 — 반드시 확인

Realization Phase 진입 전에 다음이 완료되어야 합니다: ① 모든 Gap 대안 고객 결정 완료 ② 개발이 필요한 Enhancement 사양서(Functional Spec) 초안 작성 ③ Transport 시스템 환경(DEV→QAS→PRD) 구성 확인. 이 중 하나라도 미완료 상태로 Realization을 시작하면 중간에 반드시 멈추게 됩니다.

SAC-P Sprint 실행 — Sprint 사이클 실전

SAC-P Sprint는 이론적으로는 단순하지만 실전에서는 여러 이탈 지점이 있습니다. 각 단계에서 컨설턴트가 주의해야 할 것을 정리합니다.

단계컨설턴트 역할실전 주의점
Sprint 계획 백로그에서 Sprint 목표 선정, 작업 분해, 공수 배분 Sprint 내 완료 가능한 분량만 선정 — 과욕 금지. "Done의 정의"를 팀 전체가 합의해야 함
데일리 스탠드업 진행 상황 공유, 블로커(장애물) 즉시 노출 15분 엄수. 블로커를 숨기지 않는 문화가 핵심. 고객 참여가 어려우면 주 2회 간략 동기화로 대체
개발·구현 Data Action, Story, 모델 설계·구현 Sprint 중 백로그 추가 요청은 즉시 수용 금지 → 다음 Sprint 백로그에 추가. "지금 하면 안 되냐"에 흔들리지 않아야 함
Sprint 리뷰 완성된 기능 고객 시연, 피드백 수집 시연은 실제 동작하는 기능으로. 목업(Mock-up)이나 슬라이드로 대체하면 기대치 불일치가 커짐
Sprint 회고 팀 내부 프로세스 개선 논의 고객 없이 진행. "잘 된 것, 개선할 것, 다음 Sprint에서 시도할 것" 구조로 진행
SECTION 02
Configuration vs. Enhancement 실행
설정으로 할 것과 개발로 할 것 — 그리고 SAC-P Data Action의 특수성
Configuration 작업 관리 — 변경 이력과 Transport

GR 구현에서 Configuration은 SAP 시스템의 커스터마이징 설정을 변경하는 작업입니다. 코드를 작성하지 않지만, 잘못된 설정은 코드 버그만큼 치명적입니다.

Transport 시스템 3단계

DEV (개발): 모든 Configuration·Enhancement 최초 작업 환경

QAS (품질검증): 단위 테스트·통합 테스트·UAT 환경

PRD (운영): Go-Live 후 실제 운영 환경. 직접 작업 절대 금지

⚠ 절대 금지

PRD(운영) 환경에 직접 Configuration 변경 금지. 긴급 상황이라도 DEV → QAS → PRD Transport 절차를 반드시 준수해야 합니다. 이를 우회하면 시스템 불일치가 발생하고 이후 Transport가 전부 실패할 수 있습니다.

Configuration 변경 시 반드시 기록해야 할 항목:

기록 항목왜 필요한가
변경 일시·담당자문제 발생 시 원인 추적
변경 전/후 설정값롤백 시 원복 기준
변경 이유(연결 Fit-Gap ID)설계 의도 보존, 유지보수 시 맥락 파악
Transport Request 번호DEV→QAS→PRD 이동 추적

Enhancement 개발 관리 — 사양서·협업·코드 리뷰

Enhancement는 SAP 표준 기능을 벗어난 커스텀 개발입니다. 컨설턴트는 직접 코드를 작성하지 않더라도 Functional Spec(기능 사양서) 작성의 책임자입니다. ABAP 개발자는 사양서를 보고 코드를 작성합니다. 사양서가 불명확하면 결과물도 불명확합니다.

Functional Spec 최소 구성

비즈니스 요건: 이 기능이 왜 필요한가 — 연결 Gap ID와 고객 인터뷰 발언 참조

처리 로직: 입력 → 처리 과정 → 출력을 단계별로 명시. 조건 분기(if-then) 포함

입출력 명세: 사용하는 테이블, 필드, 데이터 형식

예외 처리: 오류 발생 시 어떻게 처리할 것인가

테스트 케이스: 개발자가 자체 검증할 수 있는 시나리오 최소 3개

상황: "법인 간 이익 제거 로직을 개발해 달라"는 구두 지시로 ABAP 개발을 시작했습니다. 개발 완료 후 컨설턴트가 확인하니 고객이 원하던 로직과 달랐습니다. 재작업에 3일이 소요되었습니다.

원인: "이익 제거"의 구체적 조건(어느 계정, 어느 법인 간, 어떤 금액 기준)이 사양서에 없었고, 개발자는 자신의 이해대로 구현했습니다.

예방: Functional Spec의 처리 로직 섹션에 숫자 예시를 반드시 포함합니다. "매출 X원 → 제거 분개 Y" 형태의 구체적 수치 예시가 있으면 오해의 여지가 없어집니다.

SAC-P Data Action 개발의 특수성

SAC-P에서 Data Action은 GR의 Enhancement와 유사한 위치에 있습니다. 표준 입력·집계로 해결되지 않는 계산 로직(배분, 복사, 연산)을 구현합니다. 그러나 ABAP 개발과 다른 특수한 주의점이 있습니다.

특성내용실전 주의점
스크립트 기반 SAC Data Action은 스크립트 언어(MDX 계열)로 작성 논리 오류가 대용량 데이터에서만 드러나는 경우가 많음 → 실제 데이터 규모로 테스트 필수
데이터 모델 종속성 Data Action은 모델의 차원 구조에 강하게 결합됨 모델 차원 변경 시 관련 Data Action 전수 재검토 필요 — TO-BE 단계에서 모델을 확정해야 하는 이유
실행 순서 의존성 여러 Data Action이 순서대로 실행될 때 선행 결과가 후행에 영향 실행 순서를 문서화하고, 순서가 바뀌어도 동일 결과가 나오는지 검증
버전 간 독립성 계획 버전(Actual/Budget/Forecast)별로 Data Action이 다르게 동작할 수 있음 각 버전에서 독립적으로 테스트 케이스 실행
⚠ Data Action 개발 전 반드시 확인

배분 기준(드라이버)이 고객과 합의되지 않은 상태에서 Data Action을 먼저 개발하는 것은 위험합니다. "매출 비중으로 배분"인지 "인원 수 기준"인지 확정되지 않으면, 배분 로직 전체를 재작성해야 합니다. TO-BE Visioning에서 배분 기준을 반드시 확정해야 하는 이유가 여기에 있습니다.

이슈 로그 운영 방법

구현 단계에서 발생하는 모든 이슈는 이슈 로그에 기록되어야 합니다. 머릿속이나 메신저 대화로 관리하는 이슈는 반드시 누락됩니다.

이슈 로그는 주간 보고 시 고객과 함께 검토합니다. High 이슈가 N일 이상 Open 상태이면 에스컬레이션 기준(Kick-off에서 합의한 기준)을 적용합니다. 이슈를 숨기면 나중에 더 큰 문제로 돌아옵니다.

범위 변경 요청(CR) — 발생부터 처리까지

✗ 잘못된 CR 처리

"일단 해드리고 나중에 정산하겠습니다." — 구두로 작업 시작.

나중에 "그런 말 한 적 없다" 또는 "당연히 포함인 줄 알았다"가 됩니다.

✓ 올바른 CR 처리

영향 분석 결과를 이메일로 먼저 보냅니다. "추가 X Man-Day, 일정 Y일 조정이 필요합니다. 진행하시겠습니까?" — 고객의 회신이 서면 승인입니다.

GR (Waterfall): CR은 공식 문서로 처리됩니다. CR 번호를 부여하고, 영향을 받는 설계 문서와 Transport를 업데이트해야 합니다. Phase Gate 이후에 발생한 CR은 이미 완료된 산출물의 수정을 의미하므로 영향 분석을 더욱 엄격하게 해야 합니다.

SAC-P (Agile): CR에 해당하는 요청은 백로그 항목으로 추가합니다. 단, 현재 Sprint에 삽입하지 않고 다음 Sprint 계획 시 우선순위를 재조정합니다. Sprint 백로그 확정 후 변경은 Sprint 완료를 위협하므로 Product Owner와 협의가 필요합니다.

구현 중 추가 Gap 발견 시 처리 기준

Fit-Gap을 아무리 꼼꼼히 해도 구현 중에 새로운 Gap이 발견됩니다. 이것은 실패가 아닙니다. 중요한 것은 발견 즉시 올바르게 처리하는 것입니다.

상황처리 방향주의
Fit-Gap에서 누락된 요구사항 발견 이슈 로그 등록 → 영향도 분석 → CR 또는 범위 내 해결 결정 컨설턴트 책임인지 고객 추가 요청인지 먼저 구분
표준 기능 제약으로 설계 변경 필요 대안 솔루션 재검토 → 고객 재합의 → 설계 문서 업데이트 이미 완료된 Configuration에 영향 여부 확인 필수
데이터 품질 문제로 로직 동작 불가 데이터 정제 요청(고객 책임) → 임시 처리 로직 여부 결정 데이터 정제는 고객 책임임을 이슈 로그에 명시
SAP 릴리즈 제약(버전 미지원 기능) 대안 기능 검토 또는 Enhancement → Kick-off 전 미확인이면 컨설턴트 책임 릴리즈 확인을 Kick-off 전에 해야 했던 이유
SECTION 04
단위 테스트 — UAT 이전 품질 확보
컨설턴트가 직접 수행하는 검증의 기준
단위 테스트의 목적과 원칙

단위 테스트(Unit Test)는 구현한 기능이 설계대로 동작하는지를 UAT(고객 수락 테스트) 이전에 컨설턴트가 스스로 검증하는 작업입니다. UAT는 "고객 확인" 단계이지 "버그 발견" 단계가 아닙니다. UAT에서 기본적인 오류가 발견되면 신뢰도가 크게 떨어집니다.

⚠ 흔한 오해

"UAT에서 고객이 테스트해줄 거니까 단위 테스트는 간단히 해도 된다." — 이 생각이 UAT 실패의 가장 흔한 원인입니다. 단위 테스트에서 발견된 결함은 수정 비용이 가장 저렴합니다. UAT 이후 발견되면 재테스트·재이관 등 비용이 수 배로 증가합니다.

테스트 원칙내용
독립 검증개발/설정을 직접 한 사람이 아닌 다른 팀원이 테스트 케이스를 실행
실제 데이터테스트 데이터는 실제 업무 데이터와 동일한 구조·규모 사용
경계값 테스트정상 케이스 외에 0, 음수, 최대값, 예외 케이스를 반드시 포함
결과 기록모든 테스트 케이스의 실행 결과를 문서화. 통과/실패 판정 기준 명시
GR 단위 테스트 — 연결 로직 검증 포인트

GR 구현에서 단위 테스트는 단순히 "숫자가 나오는가"를 확인하는 것이 아닙니다. 연결 조정 로직의 정합성을 수치로 검증해야 합니다.

검증 영역테스트 케이스 예시검증 기준
ICMR 내부거래 대사 법인 A가 법인 B에 100 매출 계상 → 법인 B의 매입 100과 대사 ICMR 대사 후 차이 = 0 (또는 허용 한도 내)
투자자본상계 (C/I) 모회사 투자주식 500 + 자회사 자본 500 → 상계 후 연결 자본에서 제거 연결 재무상태표에 투자주식·자본 이중 계상 없음
지분법 (IAS 28) 관계사 당기순이익 100 × 지분율 30% = 지분법이익 30 계상 지분법이익 30이 연결 손익에 정확히 반영
외화 환산 (IAS 21) USD 1,000 × 전기말 환율 → KRW 환산 금액 정확성 검증 환산 금액 오차 없음, 환산차이 OCI 반영 확인
FS Item 집계 GL 계정별 잔액이 FS Item에 정확히 매핑되어 집계되는지 개별 GL 잔액 합계 = FS Item 잔액
✓ 수치 검증의 핵심

GR 단위 테스트에서 가장 효과적인 방법은 수작업 계산값과 시스템 결과값을 대조하는 것입니다. 예를 들어 ICMR 대사율을 Excel로 수동 계산한 후 GR 결과와 비교합니다. 일치하면 로직이 정확한 것이고, 불일치하면 Configuration이나 데이터 매핑에 오류가 있는 것입니다.

SAC-P 단위 테스트 — Data Action 결과 검증

SAC-P에서 단위 테스트는 주로 Data Action의 계산 결과가 의도한 로직대로 동작하는지 검증합니다.

검증 영역테스트 케이스 예시검증 기준
Top-Down 배분 본사 매출 목표 1,000 → LOB 비중(60:40)으로 배분 LOB A = 600, LOB B = 400, 합계 = 1,000
Bottom-Up 집계 LOB별 비용 입력 후 법인 합계 집계 집계 합계 = 입력 개별 합계, 누락·중복 없음
버전 복사 Actual 2024 데이터 → Budget 2025 시작값으로 복사 복사 후 Budget 2025 값 = Actual 2024 값, 원본 불변
계획-실적 차이 계산 Budget 1,000 - Actual 900 = Variance 100 Variance = 100, 부호 방향(+/-) 정확성 확인
데이터 초기화 특정 버전·기간의 데이터 삭제 Data Action 삭제 대상만 제거, 다른 버전·기간 데이터 보존

부호 오류: 배분 로직에서 양수/음수를 잘못 처리해 합계가 0이 되는 경우. 비용 계정(-)과 수익 계정(+)의 부호 처리를 명시적으로 테스트해야 합니다.

멤버 필터 오류: 특정 차원 멤버(법인, 제품 등)에만 적용해야 하는 Data Action이 전체에 적용되는 경우. 필터 조건을 경계값(가장 작은 집합, 가장 큰 집합)으로 테스트합니다.

0으로 나누기: 배분 기준(드라이버) 값이 0일 때 오류 처리 로직이 없어 전체 Data Action이 실패하는 경우. 드라이버 = 0인 케이스를 테스트 케이스에 반드시 포함해야 합니다.

버전 혼재: Actual 데이터를 수정하도록 설계된 Data Action이 Budget 버전에서 실행되는 경우. 버전 필터를 테스트 케이스에서 명시적으로 검증합니다.

테스트 케이스는 재현 가능해야 합니다. "해봤더니 됐다"는 테스트가 아닙니다.

✓ 테스트 케이스 최소 구성

ID: TC-GR-001 (추적 가능)
